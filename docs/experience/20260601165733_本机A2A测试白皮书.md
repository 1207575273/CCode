## 0. 这份文档解决什么

给一个明确、可复现的流程，验证「本机多个 CCode 会话能否互相寻址、互相委托任务、并让被调方看见自己被调用」。覆盖三层：

1. 自动化单元/集成测试（CI 可跑，无需起真实会话）
2. 手动端到端真机测试（起两个会话，跑通 dispatch）
3. 被调方可见反馈验证（CLI 状态栏 / Web 状态栏 / Web Agent 网格页三端）

不在范围：跨机器（不同物理机）连接 —— 那需要虚拟网卡过滤 + 鉴权，属 M3，见跨机器待办文档。

## 1. 架构速览（测之前先懂原理）

```
会话 A(端口 54751)                          会话 B(端口 54509)
   |                                            |
   | dispatch_remote_agent(agent='54509', ...)  |
   |  + message.metadata['ccode:caller']        |
   |    = {port:54751, projectName:'A'}         |
   v                                            v
 A2AClientWrapper --HTTP(127.0.0.1)--> B 的 A2A 节点(node-server)
                                                |
                                       runTask -> recordInbound(记"被调用了")
                                                |
                                       executeA2ATask -> 起 sidechain AgentLoop
                                                |
                                       流式 A2AStreamEvent 回传 A
```

要点：
- 每个会话启动后起一个独立 A2A HTTP 节点（动态端口），写 lockfile 名片到 `~/.ccode/instances/<pid>.json`。
- 本机互调统一用 `127.0.0.1`（不用局域网 IP，避开代理虚拟网卡 404 坑）。
- 被调方收到任务后起后台 sidechain AgentLoop 执行，**不进自己的主对话历史**（不打断），但会通过 `recordInbound` 记录"被调用"这件事，供状态栏/网格页展示。
- 发起方身份通过 `message.metadata['ccode:caller']` 透传，被调方据此显示"来自谁"。

关键文件：
| 文件 | 职责 |
|---|---|
| `src/a2a/node-server.ts` | 启动会话 A2A 节点（HTTP server + lockfile + 心跳） |
| `src/a2a/server-executor.ts` | AgentLoop -> A2A 流事件（纯翻译） |
| `src/a2a/inbound-recorder.ts` | 包装 inbound 流，记录被调开始/终态 |
| `src/a2a/node-status.ts` | 进程内 A2A 状态 + inbound 活动日志 |
| `src/tools/agent/dispatch-remote-agent.ts` | 发起方调用工具（带 caller 透传） |
| `src/server/a2a-routes.ts` | A2A HTTP 路由（含 `/a2a/inbound-activity`） |
| `src/server/dashboard/a2a-dashboard-api.ts` | Web 网格页数据（聚合各节点 inbound） |

## 2. 测试前置

### 2.1 环境
- Node >= 20
- 已 `pnpm install`
- 配置好至少一个可用 provider/model（`~/.ccode/config.yml`），否则被调方 sidechain 无法真正执行

### 2.2 启动方式
| 场景 | 命令 |
|---|---|
| 开发模式（带 Web） | `pnpm dev:web`（= `tsx bin/ccli.ts --web`） |
| 开发模式（纯 CLI） | `pnpm dev` |
| 构建后运行 | `ccode --web` |

A2A 节点在任意模式下都会启动（不依赖 `--web`）；但要验证 Web 状态栏与 Agent 网格页，必须带 `--web`。

## 3. 自动化测试（先跑这层，绿了再上真机）

A2A 相关单测全部位于 `tests/unit/a2a/` + 状态栏渲染测试。

```bash
# 全量 A2A + 状态栏相关
npx vitest run tests/unit/a2a/ tests/unit/StatusBar.test.ts tests/unit/useStatusBar.test.ts

# 仅本次"被调方可见反馈"相关
npx vitest run \
  tests/unit/a2a/node-status.test.ts \
  tests/unit/a2a/inbound-recorder.test.ts \
  tests/unit/a2a/a2a-routes.test.ts \
  tests/unit/a2a/a2a-dashboard-api.test.ts \
  tests/unit/StatusBar.test.ts
```

各测试文件覆盖点：

| 测试文件 | 验证什么 |
|---|---|
| `node-status.test.ts` | inbound 日志记录/读取/环形截断（最多 20 条）、active 计数 |
| `inbound-recorder.test.ts` | 流包装记 start->completed/failed、抛错记 failed 再上抛、事件透传不改写、caller 透传 |
| `a2a-routes.test.ts` | RPC 分发、SSE 流、从 `message.metadata['ccode:caller']` 提取发起方、无 metadata 时 caller 为 undefined |
| `a2a-dashboard-api.test.ts` | 跨进程聚合各节点 inbound、拉取失败降级、远程 token 脱敏、discover 抛错不崩 |
| `StatusBar.test.ts` | inbound 标签格式化（执行中/完成/失败、来源、60s 衰减窗口） |
| `node-server.test.ts` | 节点启动、lockfile、心跳、停止 |
| `dispatch-remote-agent.test.ts` | 目标解析（端口/sessionId/项目名）、流投影、错误处理 |

通过标准：上述命令 `[PASS]`，无 `[FAIL]`。

> 注意：跑全量测试时务必带 `CCODE_HOME` 重定向到临时目录（vitest 已通过 `tests/setup/ccode-home.ts` 自动隔离），避免污染真实 `~/.ccode`。

## 4. 手动端到端测试

### 4.1 场景 A：节点起来 + 服务发现

步骤：
1. 终端 1：进入项目 A 目录，`pnpm dev:web`，等待界面就绪。
2. 终端 2：进入项目 B 目录（可同目录也可不同），`pnpm dev:web`。
3. 在任一会话输入 `/a2a list`。

预期：
```
[INFO] 本机活跃会话 Agent（2）—— 可直接按项目名或会话 id 调用：

1. <项目名A>
   会话 id: 019e7ed8-...
   地址:    http://127.0.0.1:54751
   ...
2. <项目名B>
   会话 id: 019e7ed8-...
   地址:    http://127.0.0.1:54509
   ...
```

验证点：
- [ ] 两个会话都列出，端口不同
- [ ] sessionId 显示**完整**（UUIDv7 前缀同源，截断无区分度）
- [ ] 地址都是 `127.0.0.1`（不是 192.168.x / 198.18.x）

补充诊断：`node scripts/a2a-probe.mjs` 应打印发现的节点并对端口测通 well-known + RPC 路由（well-known 返回 200，POST `/` 与 `/a2a/rpc` 命中路由返回含 `-32601` 的 JSON 而非 404）。

### 4.2 场景 B：dispatch 端到端

在会话 A 让 Agent（或直接构造工具调用）执行：
```
dispatch_remote_agent(agent='54509', message='报告你的 cwd、PID、package.json version')
```
（`agent` 可填端口、完整 sessionId、或项目名）

预期返回（status=completed）：
- output 含被调方 B 的 cwd / PID / version
- **PID 必须是 B 进程的 PID**（证明任务确实在 B 执行，而非 A 自己跑）

验证点：
- [ ] status = completed
- [ ] 返回内容来自 B（PID/cwd 对得上 B）
- [ ] A 的界面把这次远程调用渲染成 SubAgent 卡片（复用现有卡片）

### 4.3 场景 C：被调方可见反馈（本次新功能，重点）

承接场景 B：在 A 发起 dispatch 的**同时**，观察被调方 B。

#### C-1 CLI 状态栏（B 的终端）
任务执行中，B 底部 INFO 行出现：
```
INFO  ... | A2A http://127.0.0.1:54509 | 被调 <来源> 执行中
```
任务完成后 60 秒内：
```
INFO  ... | 被调 <来源> 3秒前 完成
```
- `<来源>` 优先显示发起方项目名，无项目名显示 `:端口`，再无显示 `远程`
- 颜色：执行中 cyan，完成 green，失败 red
- 超过 60 秒后该提示自动消失（只保留 A2A 地址标记）

验证点：
- [ ] B 执行中 INFO 行出现"被调 ... 执行中"
- [ ] 来源显示为 A 的项目名或端口（证明 caller 透传生效）
- [ ] 完成后短时显示"完成"，60s 后消失
- [ ] **B 的主对话历史没有被注入任何内容**（不打断原则）

#### C-2 Web 状态栏（B 的 Web 页，需 `--web`）
打开 B 的 Web（终端日志里有地址，通常 `http://127.0.0.1:9800/...`），底部状态栏 INFO 行同样出现"被调 ... 执行中 / 完成"，配色与 CLI 一致。

验证点：
- [ ] Web 状态栏与 CLI 状态栏表现一致（数据经 `status_bar` WS 事件同步）

#### C-3 Web Agent 网格页（`/agents`）
打开任一带 `--web` 会话的 Web，进入「Agents / Agent 网格」页（侧边栏）。在「列表」视图，B 的会话卡片底部出现「被调用」区：
```
被调用   [N 个执行中]
  执行中  <来源>   <任务预览>
  完成    <来源>   <任务预览>
```

验证点：
- [ ] B 的卡片出现"被调用"区，列出最近调用记录（最多 5 条）
- [ ] 进行中任务有"N 个执行中"徽章
- [ ] 状态颜色/来源/任务预览正确
- [ ] 该数据是**跨进程聚合**：在 A 的 Web 也能看到 B 卡片的被调记录（dashboard 拉取 B 节点的 `/a2a/inbound-activity`）

> 原理：inbound 活动是各会话**进程内**状态。Web 网格页通过 dashboard 并行拉取每个本机节点的 `/a2a/inbound-activity` 端点聚合，所以在任一会话的 Web 都能看到全网格的被调情况；而状态栏（C-1/C-2）只反映**本会话自己**被调的情况。

### 4.4 场景 D：拓扑视图
`/agents` 页切到「拓扑」Tab：中心是「本机 CCode」，内环是本机会话节点，外环是远程已信任 Agent。

验证点：
- [ ] 两个会话都出现在内环，标注项目名 + sessionId 前 6 位 + 端口
- [ ] 连线/空态渲染正常

### 4.5 场景 E：异常路径

| 子场景 | 操作 | 预期 |
|---|---|---|
| 目标不存在 | `dispatch_remote_agent(agent='99999', ...)` | status=failed，提示不在白名单/未发现 |
| 被调方任务失败 | 让 B 执行一个必然报错的指令 | A 拿到 status=failed；B 的"被调"标记显示**失败**(red) |
| 被调方中途退出 | dispatch 执行中 kill 掉 B | A 侧报错；B 的 lockfile 由其他会话 scanner 在 30s 内清理 |

## 6. 排错手册（踩过的坑）

| 现象 | 根因 | 处理 |
|---|---|---|
| dispatch 返回 404 | `getLanHost()` 探到代理/VPN 的 TUN 虚拟网卡（如 Clash 的 `198.18.0.0/15`），card.url 指向它被代理拦截 | 本机统一用 `127.0.0.1`（已写死）；用 `node scripts/a2a-probe.mjs` 看 card.url 是否 127.0.0.1 |
| `/a2a list` 看不到另一个会话 | 另一会话没起 A2A 节点 / lockfile 没写 / hostname、osUser 不匹配 | 查 `~/.ccode/instances/` 是否有对方 `<pid>.json`；跑 a2a-probe |
| 同名会话分不清 | 同目录起多个会话，项目名相同 | 用端口或完整 sessionId 调用（端口唯一） |
| 被调方状态栏无"被调"提示 | 该会话不是 A2A 节点 / 没真正收到 inbound / 已超过 60s 衰减窗口 | 确认 INFO 行有 `A2A http://127.0.0.1:...` 标记；dispatch 后立即观察 |
| Web 网格页看不到别会话的被调记录 | 目标节点 `/a2a/inbound-activity` 不可达（进程退出/端口变化） | dashboard 会降级为缺省（该卡片无被调区）；确认目标会话仍活跃 |
| caller 显示"远程"而非项目名 | 发起方不是 A2A 节点，metadata 未带 caller | 确认发起会话也起了 A2A 节点（INFO 行有 A2A 标记） |

诊断脚本：
```bash
node scripts/a2a-probe.mjs     # 读 lockfile -> 测 well-known + RPC 路由
```

## 7. 已知边界（当前不支持，非 bug）

- 跨物理机连接：未启用（需虚拟网卡过滤 + 鉴权，见跨机器待办）。
- inbound 记录不持久化：仅进程内内存，会话退出即消失；环形日志最多保留 20 条。
- 本机 localhost 无鉴权：同机受信，跨机器前必须补鉴权（D-15/D-16）。
- Web 完整 Task 时间轴/回放：属 M3 `a2a_tasks` 持久化，当前仅有轻量"被调用"活动展示。
