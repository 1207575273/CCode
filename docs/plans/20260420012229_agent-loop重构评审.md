## 1. 背景

### 1.1 AgentLoop 在 cCli 里是什么角色

cCli 的执行核心是 **LLM ↔ Tools 多轮对话**:每次用户提问 → 调 LLM → 如果有 `tool_call` 就执行工具 → 把 `tool_result` 追加回 history → 再调 LLM,直到 LLM 只产生纯文本为止。

`AgentLoop` 类就是这个循环的载体。它的正确与否直接决定:

- 主 Agent 聊天是否正常;
- 子 Agent (`dispatch_agent`) 是否能稳定完成子任务;
- Hook / 权限检查 / 重复检测 / Prompt Cache 等横切能力是否真的生效;
- 观测事件(SessionLogger JSONL)是否完整,用于 Web Dashboard 回放。

### 1.2 为什么现在需要评审

三个触发点让 agent-loop 的边际成本明显上升:

1. **功能密度**已达临界**:** 并行工具、StreamableTool、Hook(Pre/Post)、重复检测、子 Agent 嵌套、Prompt Cache 破裂检测、后台执行(run_in_background)、minTurns 续跑、stopRequested 优雅退出 —— 这些全部内聚在同一个类里,新增能力的心智成本陡增。
2. **实战事故的伤疤**已经形成注释墙**:** 文件头那段"雷区一/二/三/四"是过往事故的蒸馏(tool_call 孤儿、异常 stack 丢失、SubAgent 继承 system prompt、循环退出条件误判),说明逻辑本身已经到了"需要大量防御性注释才敢改"的临界点。
3. **对标 Claude Code 的计划**(见 `20260419153000_对标ClaudeCode能力差距与下阶段规划.md`)里,Checkpoint/Rewind、更细粒度的事件总线、可插拔策略层都会再往 agent-loop 里加东西 —— 如果不先做职责切分,继续往上堆只会加速腐化。

### 1.3 本文档的定位

**这不是代码 diff,这是方案评审。** 产出物只有三样:

- 问题清单(现象 + 根因 + 影响范围 + 证据位置)
- 分级重构方向(P0 / P1 / P2)
- 前置条件和风险警告

任何具体代码改动都需要另起一份落地方案,绿色测试矩阵到位之后才动手。

### 🔴 P0-01 并行工具路径与串行工具路径行为不一致

#### 现象

同一个工具调用,走并行分支和走串行分支时,得到的"护栏能力"是不一样的。

| 能力 | 串行 `#executeOneTool` | 并行 `executeSingleTool` |
|------|---|---|
| 重复调用检测(RepetitionDetector) | ✅ 在权限检查之前执行 | ❌ 完全没有 |
| PreToolUse Hook | ✅ 可 block / 可 modify 参数 | ❌ 没有 |
| PostToolUse Hook(Reflection 闭环) | ✅ 注入 additionalContext 到 history | ❌ 没有 |
| tool_done 是否携带 `meta` | ✅ | ❌(`parallel-executor.ts:168-176` 未注入 meta 字段) |
| tool_result 写入 history 的粒度 | 每工具一条 user 消息 | 同一批的 N 个工具合并成一条 user 消息 |

> 📌 **勘误**:初稿曾列"截断阈值 40K vs 100K"为不一致项,经核对两条路径写入 history 均走 `truncateForLLM` 40K、写入 `tool_done.resultFull` 均为 100K,**行为一致**。真实问题只在 P0-02 "常量定义重复"那一层。

#### 根因

并行执行逻辑是后加的:`parallel-executor.ts` 里 `executeSingleTool` 实际上是把 `#executeOneTool` 的一个精简子集**复制了一遍**,只保留了「调用 registry.execute + 发射 tool_start/tool_done」两个环节,其他护栏没有同步搬运。

#### 影响

- **LLM 一次派发 5 个相同 grep 时,RepetitionDetector 不会拦截**(并行路径根本不查指纹)。
- **PostToolUse Hook 在并行工具里静默失效**。如果用户靠 hook 做 tsc 验证反馈,一旦工具被归为 safe 并行,反馈就丢了。
- **tool_done 事件缺失 `meta` 字段**,下游依赖 meta 的 UI/观测消费者对并行工具失效。

#### 证据位置

- `cCli/src/core/agent-loop.ts:482-531` `#executeToolCalls` — 两条分叉路径的源头。
- `cCli/src/core/agent-loop.ts:541-706` `#executeOneTool` — 完整护栏链(165 行)。
- `cCli/src/core/parallel-executor.ts:141-212` `executeSingleTool` — 精简子集,缺失护栏。
- `cCli/src/core/parallel-executor.ts:168-176` `tool_done` 事件构造,未带 `meta` 字段。

#### ✅ 已解决(S-P0.1 / commit `d3fa6e3`)

两条路径现统一走 `core/tool-pipeline.ts` 的 `executeToolPipeline()`:
- 串行:`agent-loop.ts:#executeOneTool` 直接 `yield* executeToolPipeline(...)`。
- 并行:`parallel-executor.ts` 对每个工具跑 pipeline,合并 `outcome.toolResult` 到同一条 user 消息(Anthropic 协议要求)。
- RepetitionDetector / Pre+PostHook / `tool_done.meta` 三处静默失效 bug 一次性消除。
- StreamableTool(如 `dispatch_agent`)在 `classifyToolCalls` 中归入 dangerous 走串行路径,避免并行 drain 打乱事件顺序。

### 🔴 P0-02 截断策略散落,存在三套常量、两个函数

#### 现象

输出截断/摘要这件事,项目里同时存在:

- `agent-loop.ts:182-187` 定义 `RESULT_SUMMARY_MAX_LENGTH=200`、`RESULT_FULL_MAX_LENGTH=100_000`、`LLM_RESULT_MAX_CHARS=40_000`
- `parallel-executor.ts:41-43` 定义 `RESULT_SUMMARY_MAX_LEN=200`、`RESULT_FULL_MAX_LEN=100_000`(缺少第三个)
- `agent-loop.ts:733-738` `truncate()` 带隐晦分支:`maxLength >= 10000` 给 "(truncated, total N chars)" 后缀,否则只给 "..."
- `agent-loop.ts:741-757` `truncateForLLM()` 另有一套"工具专属截断后引导文案"(`TRUNCATION_HINTS` 字典),只在串行路径生效

#### 根因

截断策略没有作为独立的横切关注点抽出来,而是随写随加常量,后续新增的调用点就地 import 最近的那一套。

#### 影响

- 维护者要改 200 这个阈值,可能只改了一处;
- 同一段工具输出,在 UI 卡片 / LLM history / SessionLogger JSONL 里长度可能不同,调试回放时极易误导;
- `TRUNCATION_HINTS` 只在串行路径生效这件事,没有代码或注释说明,属于"静默残疾"。

#### 证据位置

- 见现象小节列举的四段常量/函数定义。

#### ✅ 已解决(S-P0.2 / commit `0bb4624`)

新增 `core/result-truncator.ts`(79 行)独占所有常量:
- `SUMMARY_MAX_CHARS = 200` / `FULL_MAX_CHARS = 100_000` / `LLM_MAX_CHARS = 40_000`
- 导出四个纯函数:`truncate` / `truncateForSummary` / `truncateForFull` / `truncateForLLM`
- `TRUNCATION_HINTS`(工具专属截断引导语)现由 `truncateForLLM` 统一消费,并行/串行一视同仁。
- 原 `agent-loop.ts` / `parallel-executor.ts` 中的重复常量与函数全部删除,改为 import。
- `tests/unit/core/result-truncator.test.ts` 覆盖 18 条用例。

### 🔴 P0-03 AgentLoop 是上帝类,职责失守

#### 现象

`AgentLoop` 单一个类里同时承担:

| # | 职责 | 代码位置 |
|---|------|------|
| 1 | 主循环控制(turns / stopRequested / minTurns 续跑) | run() 245-309 |
| 2 | LLM 流式调用 | #callLLM 321-455 |
| 3 | StreamChunk → AgentEvent 映射 | #mapChunk 458-473 |
| 4 | 性能指标(TTFT / E2E / TPS)计算 | 内嵌 #callLLM |
| 5 | Prompt Cache 指纹/破裂检测 | 内嵌 #callLLM 404-417 |
| 6 | 工具调用分组(safe / dangerous)+ 串并行编排 | #executeToolCalls 482-531 |
| 7 | 单工具全生命周期编排 | #executeOneTool 541-706 |
| 8 | 权限检查 + 用户交互 | #checkPermission 709-726 |
| 9 | Hook(Pre/Post Tool)集成 | 内嵌 #executeOneTool |
| 10 | history 写入 + 截断策略应用 | 散落全文 |

#### 根因

没有显式的"中间层"抽象。AgentLoop 既是控制流的 owner,又是每个子能力的直接实现者。

#### 影响

- **单元测试成本高**:想单测"工具执行一次带 Hook",必须构造 provider / registry / config / hookManager / history 五件套 + fake AsyncGenerator,比单元测试应有的颗粒度大一个量级。
- **改动的震荡面广**:新增一步流程(例如"工具执行前 dry-run 校验")不得不再插入到 #executeOneTool 的 165 行长函数里,再为下一个维护者留一条新的"⚠️ 雷区"注释。
- **代码复用不可能**:子 Agent 走 dispatch_agent StreamableTool 时,相当于"嵌套一个 AgentLoop",但所有护栏(重复检测、Hook)都得重新实例化,无法只复用"单工具执行"这一片。

#### 证据位置

- `cCli/src/core/agent-loop.ts:193-727` 整个类。

#### ✅ 已解决(S-P1.1 + S-P1.2 + S-P0.1 / commits `aaf248b` `89392ad` `d3fa6e3`)

10 项职责外迁清单:

| # | 原职责 | 现位置 |
|---|---|---|
| 1 | 主循环控制 | `agent-loop.ts#run` 薄壳(保留) |
| 2 | LLM 流式调用 | `llm-call-session.ts#invoke` |
| 3 | StreamChunk → AgentEvent 映射 | `llm-call-session.ts#mapChunkToEvent` |
| 4 | 性能指标(TTFT/E2E/TPS) | `llm-call-session.ts` 内嵌 |
| 5 | Prompt Cache 指纹/破裂检测 | `llm-call-session.ts` 内嵌(per-session 持久) |
| 6 | safe/dangerous 分组 + 并发编排 | `parallel-executor.ts#classifyToolCalls` |
| 7 | 单工具全生命周期 | `tool-pipeline.ts#executeToolPipeline`(8 阶段) |
| 8 | 权限检查 | `tool-pipeline.ts` 第 2 阶段内嵌 |
| 9 | Pre/Post Hook | `tool-pipeline.ts` 第 3/7 阶段内嵌 |
| 10 | history 写入 + 截断 | `history-writer.ts` + `result-truncator.ts` |

最终 `agent-loop.ts` 只保留主循环 + 工具分发 + 终止判断三件事,从 824 行瘦身到 356 行。

### 🟡 P1-01 AgentEvent 联合类型混入 4 类语义

#### 现象

`AgentEvent` 是一个 union type,包含 20+ 个分支,但这些分支语义上分属 4 类:

- **业务事件**(UI 消费):`text` / `thinking` / `tool_start` / `tool_done` / `permission_request` / `user_question_request` / `error` / `done`
- **观测事件**(SessionLogger JSONL 消费):`llm_start` / `llm_done` / `llm_error` / `tool_fallback` / `permission_grant` / `post_tool_feedback`
- **子 Agent 事件**(dispatch_agent 透传):`subagent_spawn` / `subagent_progress` / `subagent_done`
- **规划事件**(useChat 广播):`todo_update`

#### 根因

事件从"AsyncGenerator 单通道 yield"这个朴素模型开始演化,每新增一个语义类别就并入同一个 union,没有为类别建抽象层。

#### 影响

- 消费者(useChat / SessionLogger / Web Bridge)必须对所有 20+ 分支做 switch,漏判会触发静默丢事件;
- 新增一个事件类型,要同步改主 Agent、dispatch_agent、useChat 分发、SessionLogger 分类、Web API 转发 —— 穿透整栈;
- 类型系统无法约束"这个事件应该被谁消费",全靠注释提醒。

#### 证据位置

- `cCli/src/core/agent-loop.ts:77-142` AgentEvent 定义块。

#### ✅ 已解决(S-P1.3 / commit `cd6405a`)

新增 `core/agent-events.ts`(143 行),按语义拆为 4 个子 union:

```ts
type BusinessEvent      = ...  // 业务事件(UI 消费)
type ObservabilityEvent = ...  // 观测事件(SessionLogger 消费)
type SubagentEvent      = ...  // 子 Agent 事件(dispatch_agent 透传)
type PlanningEvent      = ...  // 规划事件(todo_update)
type AgentEvent         = BusinessEvent | ObservabilityEvent | SubagentEvent | PlanningEvent
```

`agent-loop.ts` 保留 re-export 做向后兼容,现有消费者零改动;新消费者可只 switch 自己关心的子 union,类型系统自动发现缺失分支。

### 🟡 P1-02 Hook 扩展点硬编码,不可泛化

#### 现象

目前 Hook 只支持 `PreToolUse` / `PostToolUse` 两个挂载点,位置硬编码在 `#executeOneTool` 内部的两处 `if (this.#config.hookManager)` 块。

#### 证据位置

- `cCli/src/core/agent-loop.ts:584-617` PreToolUse 块。
- `cCli/src/core/agent-loop.ts:676-695` PostToolUse 块。

### 🟢 P2-01 并行工具事件延迟 yield 导致 UI 非流式

#### 现象

`#executeToolCalls` 并行分支里,所有 tool_start / tool_done 事件先被收集进 `events: AgentEvent[]` 数组,等 `Promise.allSettled` 全部结束后一次性 yield 出去(`agent-loop.ts:500-508`)。

#### 根因

AsyncGenerator 在 `for await...of` 内部不能被多路并发 yield,所以只好缓冲事件、等到 await 之后统一发射。

#### 影响

- UI 上看到的是"一批 5 个工具同时开始、同时结束",而不是"先开始的工具 tool_start 先显示";
- 对于 > 2 秒的 bash / grep 工具,用户感知"卡住没反应",体验差。

#### 证据位置

- `cCli/src/core/agent-loop.ts:498-525` 并行 safe 工具的整个执行块。

#### ⏸️ 推迟(S-P2.3)

属于 UI 体验优化,复杂度高(涉及 JS async scheduling),收益仅为"事件到达时序"而非正确性;推迟到 EventBus(S-P2.2)之后再处理。

## 3. 解决方案 — 分级重构方向

**原则**:先消除风险,再做职责切分,最后才是扩展点泛化。每一级完成后系统都可交付、可回滚。

### P0 — 必做,消除正确性风险

#### S-P0.1 统一工具执行管道

**目标**:消除并行与串行两条路径的护栏差异,让"一次工具调用"有唯一的执行路径。

##### 三种候选实现(需决策方选一种)

| 方案 | 形态 | 优点 | 代价 |
|---|---|---|---|
| **A. 拦截器链类** | `ToolExecutor` + 7 个 `Interceptor` 类 + runner | 每步可单测、可按配置增删 | 新增 ~150-250 行基础设施,过度工程化风险 |
| **B. 单函数 pipeline** | 一个 `executeToolPipeline(tc, ctx)` 顺序调用现有 hookManager / detector / writer | 改动最小,现有模块即插即用 | 长函数仍存在,只是从 165 行降到 ~90 行 |
| **C. 装饰器组合** | `compose(withRepetition, withHook, ...)(coreExec)` | 函数式优雅,灵活拼装 | 要求团队熟悉函数式风格,堆栈追踪相对难读 |

**推荐起点**:**方案 B(单函数 pipeline)**。理由:投入产出比最高,先消灭护栏差异这个正确性 bug;至于"是否进一步抽成拦截器类"等稳定运行后再决定。方案 A 留给"事实证明需要更多扩展点时"的第二阶段。方案 C 除非团队已经是函数式风格爱好者,否则不推。

##### 流程(不区分具体方案)

```
tool_start 发射
  → [重复检测]
  → [权限检查(Sidechain 跳过)]
  → [PreToolUse Hook(可 block / 可 modify args)]
  → [核心执行(registry.execute 或 streamableTool.stream)]
  → [结果截断 + history 追加]
  → [PostToolUse Hook + Reflection 反馈]
  → tool_done 发射

并行 = Promise.allSettled N 条独立 pipeline;串行 = 顺序跑 N 次。
```

##### 关键待定决策(动代码前必须回答)

1. **错误传播语义**(三个子问题):
   - PreHook 抛异常 → 中断 pipeline 还是继续?**建议**:中断,产生 `isError: true` 的 tool_result,保留雷区一防御。
   - 核心执行抛异常 → PostHook 是否仍跑?**现状**:PostHook 仍跑,依赖外层 try/catch;迁移时保持此行为。
   - pipeline 内任何一步 throw 后,tool_call 是否一定有对应 tool_result?**建议**:用类型系统 + runner 层兜底双保险,不只靠注释。

2. **子 Agent 嵌套(`dispatch_agent`)的 pipeline 策略**:
   - 选项 a:子 AgentLoop 独立实例化新 pipeline(当前心智模型)
   - 选项 b:子/主共享 pipeline 实例但拦截器按 flag 开关(RepetitionDetector **必须**独立计数器,Hook 可共享)
   - **建议**:选 a,简单可理解;Hook 是否在子 Agent 触发由 config flag 显式控制并写进注释(同时解决原 P2-02 的文档债)。

3. **tool_done 事件发射是否属于 pipeline 的一步**:
   - 架构洁癖角度,事件发射是**副作用**不是**处理步骤**。
   - **建议**:放在 pipeline 外的 runner 层统一发射,ctx 提供 `emit()` 能力供中间态事件(tool_start / subagent_progress)使用。

**解决的问题**:P0-01 的全部护栏差异(RepetitionDetector / Pre/PostHook / tool_done.meta 三处缺失)。

**前置依赖**:E2E 测试矩阵(§5.1)先绿 + 上述 3 个待定决策有书面结论。

#### S-P0.2 截断策略单模块收敛

**目标**:新增 `core/result-truncator.ts`,独占所有截断常量 + 纯函数 API。

**接口草案**:

```
truncateForSummary(text)   → ≤200 字符,给 UI 卡片用
truncateForFull(text)      → ≤100K 字符,给 Web 回放用
truncateForLLM(text, tool) → ≤40K 字符 + 工具专属引导语,给 history 用
```

`agent-loop.ts` / `parallel-executor.ts` 两处 import 同一份,原常量全部删除。

**解决的问题**:P0-02。

**前置依赖**:无。可独立先做,是 S-P0.1 的前置。

### P1 — 强烈建议,职责切分

#### S-P1.1 抽出 LLMCallSession

**目标**:把 `#callLLM` + `#mapChunk` + 性能指标 + 缓存指纹检测全部搬到独立模块。

```
class LLMCallSession {
  async *invoke(provider, request): AsyncGenerator<AgentEvent, LLMResult>
  // 内部负责 TTFT/TPS 埋点、cache fingerprint、stopReason 标准化
}
```

AgentLoop.run() 瘦身为三步清单:

```
1. llmResult = yield* session.invoke(provider, buildRequest(history))
2. 把 assistant 消息和 toolCalls 摘要写入 history
3. yield* toolExecutor.executeBatch(llmResult.toolCalls, history)
```

**解决的问题**:P0-03 的 2/3/4/5 项职责外迁;同时为 provider stopReason 词汇表统一(见 P1-03 勘误 2)提供落脚点。

#### S-P1.2 抽出 HistoryWriter

**目标**:所有 `history.push(...)` 收敛到一个类,外层只看到三个方法:

```
writer.appendAssistant(text, toolCalls)
writer.appendToolResult(toolCallId, rawOutput, toolName, isError)
writer.appendSystemNote(text)   // 给 RepetitionDetector warn / 续跑消息等用
```

内部负责:args summarize、result 截断、tool_call ↔ tool_result 成对校验(雷区一硬检查)。

**解决的问题**:P0-03 的第 10 项职责外迁;雷区一的防御从"靠注释提醒"升级为"类型 + 运行时双保险"。

#### S-P1.3 AgentEvent 按语义拆分为三个 union

**目标**:

```
type BusinessEvent    = ... // 8 个业务分支
type ObservabilityEvent = ... // 6 个观测分支
type SubagentEvent    = ... // 3 个子 Agent 分支
type PlanningEvent    = ... // todo_update 一个
type AgentEvent       = BusinessEvent | ObservabilityEvent | SubagentEvent | PlanningEvent
```

消费者可以只 switch 自己关心的那一个子 union,类型系统自动发现缺失分支。

**解决的问题**:P1-01。

### P2 — 长期演进

#### S-P2.1 Hook 泛化为中间件接口

**目标**:Pre/Post Tool + Pre/Post LLM + OnTurnStart + OnStop 统一为 `Middleware<T>` 接口,挂在 AgentLoop 的拦截点注册表上。

**解决的问题**:P1-02。

**前置依赖**:S-P0.1 落地。

#### S-P2.2 EventBus 订阅模型

**目标**:用 `subscribe(channel, handler)` 取代 AsyncGenerator 单消费者模式。SessionLogger、Web Bridge、UI 各自订阅,互不阻塞。

**注意**:这是一个**大破大立**改动。目前 AsyncGenerator + yield 还能扛住,**不建议现在就上**。只有当多消费者耦合成本明显超过迁移成本时再启动(预估窗口:Checkpoint/Rewind 落地之后)。

#### S-P2.3 并行工具事件流式化

**目标**:解决 P2-01。方案:并行工具内部用 `EventEmitter` 或 async channel 立即发射事件,主 AgentLoop 通过独立协程 drain。

**注意**:复杂度高(涉及 JS 的 async scheduling),收益只是 UI 体验改善,**不建议在 EventBus 之前做**。

## 5. 前置条件与风险警告

### 5.1 必须先做的事(强制)

**在动 P0 代码之前,先补齐 E2E 测试矩阵**,覆盖:

- [ ] 纯文本轮 / 纯工具轮 / 混合轮的 yield 事件顺序
- [ ] 并行 3 safe 工具 + 1 dangerous 工具的事件顺序与 history 正确性
- [ ] PreToolUse Hook `block` / `modify` 两种分支
- [ ] PostToolUse Hook `additionalContext` 注入链路
- [ ] RepetitionDetector 触发 warn / block 两级
- [ ] 子 Agent(isSidechain)嵌套 + StreamableTool(`dispatch_agent`)事件透传
- [ ] abort / max_turns / stopRequested 三种退出分别产生正确的 done.reason
- [ ] Prompt Cache fingerprint 冷启动 / 热启动 / 变化三种情形
- [ ] 工具异常(throw)时 tool_result 必须存在(雷区一)
- [ ] minTurns + isSidechain + isBackground 三种 flag 的续跑逻辑

**没有这层安全网,重构会踩雷区。** 任何一步走错,最快的后果是 Anthropic API 返回 400(`tool_call` 无对应 `tool_result`)、最隐蔽的后果是 SessionLogger JSONL 少字段导致 Web 回放残缺。

### 5.2 范围控制(建议)

- **建议**把 P2 的改动(EventBus / Hook 泛化)留在独立批次。大破大立和护栏修复最好不在同一个 PR,便于回滚。
- **建议**不借重构之名顺手加新功能。Checkpoint/Rewind、Pre/Post LLM Hook 等能力推迟到 P0/P1 全绿后,作为独立特性再议。
- 每级落地后 **建议至少跑一周真实会话**(主 Agent + 子 Agent 两条路径)再进下一级。

### 5.3 放弃的选项(有意识不做)

- 不引入 RxJS / xstate / 依赖注入框架。AsyncGenerator + 函数 pipeline 足够覆盖当前可预见的 6 个月路径。
- 不重写 Provider 抽象。当前 `LLMProvider.chat()` AsyncIterable 接口足够稳定。
- 不为子 Agent 单独设计新执行引擎。`dispatch_agent` 的 StreamableTool 嵌套 AgentLoop 模型就是正确的,重构目的正是让嵌套时能复用护栏。

### 5.4 重构期间的灰度策略

P0.1 落地时需提前决策:

- **选项 1 — 整体替换**:一次性切换到新执行路径,旧代码直接删除。优点:无分支,心智简单。缺点:回滚只能靠 git revert,期间若发现回归成本高。
- **选项 2 — feature flag 并存**:通过 env 或 config 开关切新旧路径,两周灰度。优点:线上可即时回退。缺点:两套代码并存期需要清理,否则腐化风险。

**建议**:cCli 是 CLI 工具不是长时运行服务,灰度能力价值有限;配合 §5.1 的 E2E 测试矩阵 + §5.2 "跑一周真实会话"机制,选项 1 够用。

## 7. 一句话结论

**AgentLoop 的"重"不是 824 行本身,而是 God Class × 并行/串行护栏缺失 × 横切关注点硬编码** —— 三个问题叠加形成的维护坡度(截断常量重复是小修,不构成结构性问题)。

投入产出比最高的一刀是 **P0.1 统一工具执行管道**:既消灭并行路径下 Hook / 重复检测 / tool_done.meta 三处静默失效的隐蔽 bug,又为 P1 的所有职责切分铺平轨道,是整份方案里优先级最高、收益最直接的一步。**建议以最小方案(单函数 pipeline)起步,更复杂的抽象等真实需求触发**。
