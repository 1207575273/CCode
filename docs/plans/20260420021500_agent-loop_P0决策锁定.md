### 决策 4 的偏离说明

**锁定**:pipeline 外由 runner 统一发射 `tool_done`,pipeline 只负责计算 + 写 history。

**实际落地**:`tool_done` 事件在 `tool-pipeline.ts` **内部**通过 `yield` 发射(第 1 / 4 / 7 阶段都有分支 yield `tool_done`)。runner(`parallel-executor.ts#drainPipeline` / `agent-loop.ts#executeOneTool`)只负责把 AsyncGenerator 抽干或 `yield*` 透传。

**偏离原因**:`tool-pipeline.ts` 本身已经是 AsyncGenerator,"pipeline 内部 yield 事件"和"外部 runner 发射"在 AsyncGenerator 语义下实际等价;硬性外置反而引入额外回调协议。ctx 提供 `emit()` 的设想在实施时被 AsyncGenerator 的 `yield` 原生能力替代。

**后果评估**:**无负面影响**。事件发射的职责依然只在一处(pipeline 文件内),未来接入 AgentEventBus(P2.2)时迁移点依然集中,与决策初衷一致。

### 遗留未做的 P1.1 可选项

决策 6 提到的"**两家 provider stopReason 词汇表统一**"未落地 —— LLMCallSession 直接消费 `doneStopReason` 原值,未做翻译表。影响范围:如未来出现基于 stopReason 的自动续跑策略,需在此处补一层。当前无此需求,不处理。

## 2. 六项决策的锁定结果

### 决策 1 — 统一工具执行管道的实现形态

**锁定**:方案 B — **单函数 pipeline**(`executeToolPipeline(tc, ctx)` 顺序调用现有 hookManager / detector / writer)。

**理由**:
- 投入产出比最高:先消灭护栏差异这个正确性 bug,不引入 7 个 Interceptor 类的架子。
- 现有模块(HookManager / RepetitionDetector)已经独立单测,pipeline 函数只是胶水,改动最小。
- 若未来事实证明扩展点不够,方案 A(拦截器链类)可以作为第二阶段演进,且 B 到 A 的迁移代价小于 C 到 A(C 是函数式组合,堆栈难读不利排查)。

**切换成本**:
- B → A:中等。需新增 `ToolExecutor` + `Interceptor` 接口,pipeline 函数拆为多个 class,约 150-250 行新增。
- B → C:小。但除非团队倾向函数式风格,否则无意义。

---

### 决策 2 — 错误传播语义(三个子决策)

**锁定 2.1**:PreHook 抛异常 → **中断 pipeline**,立即产生 `isError: true` 的 tool_result,保留雷区一防御。

**锁定 2.2**:核心执行(registry.execute / StreamableTool.stream)抛异常 → **PostHook 仍跑**(保持现状)。依赖外层 try/catch,结果交给 PostHook 后还有机会注入 `additionalContext` 诱导 LLM 修正。

**锁定 2.3**:pipeline 内任何一步 throw 后,tool_call 必有对应 tool_result。落地方式:
- 类型层:pipeline 函数返回类型强制为 `Promise<ToolPipelineResult>` 且 `ToolPipelineResult` 必含 tool_result;
- 运行时层:pipeline 外层 runner 套 try/catch 做最终兜底,极端情况下注入 `{ isError: true, result: 'pipeline internal error: <stack>' }`。

**理由**:保留现有"雷区一/二"注释墙蒸馏出的行为约束。中断 PreHook 有明确语义(block 的本意),而核心抛错后仍跑 PostHook 是 Reflection 闭环的关键(tsc 校验、自动修正依赖这个)。

---

### 决策 3 — 子 Agent 嵌套的 pipeline 策略

**锁定**:选项 a — **子 AgentLoop 独立实例化新 pipeline**。

**理由**:
- 心智模型简单:一个 AgentLoop = 一条自己的 pipeline。
- RepetitionDetector **必然需要独立计数器**(子 Agent 的写文件不应被主 Agent 的计数所污染),选 b 反而要额外加 flag。
- Hook 是否在子 Agent 触发,由 `AgentConfig.hookManager` 的 undefined / defined 天然控制(子 AgentLoop 构造时可以选传或不传)。

**配套动作**:在 `agent-loop.ts:584` PreHook 块上方加注释,说明"子 Agent 默认也执行 Hook,若业务要求子集化 hook,请在此处按 isSidechain 做开关"。(同时解决原评审 P2-02 的文档债)

---

### 决策 4 — tool_done 事件发射是否属于 pipeline 的一步

**锁定**:**pipeline 外由 runner 统一发射**。pipeline 只负责计算结果 + 写 history,runner 层在 pipeline 返回后发 `tool_done`。

**ctx 增强**:ctx 提供 `emit(event)` 能力,供中间态事件(`tool_start` / `subagent_progress` 等)在 pipeline 内部按需发射。

**理由**:副作用(事件发射)与处理步骤(计算/写入)分离,方便未来接入 AgentEventBus(P2.2)时只改 runner 层。

---

### 决策 5 — 灰度策略

**锁定**:选项 1 — **整体替换**,旧 `executeSingleTool` 和 `#executeOneTool` 在同一个 PR 删除。

**理由**:
- cCli 是 CLI 工具,不是长时运行服务,feature flag 灰度价值有限;
- §5.1 的 E2E 测试矩阵 + "跑一周真实会话"的外部验证足以替代灰度;
- 两套代码并存期的维护成本明显大于 git revert 的成本。

**回滚路径**:若整体替换后发现回归,直接 `git revert` 到前一个 commit,不再重开新 PR。

---

### 决策 6 — P1-03 的实测验证

**锁定**:**静态代码分析已结论,无需实测脚本**。P1-03 问题**不成立**,从清单剔除。

**依据**(2026-04-20 代码核对):
- `providers/anthropic.ts:272` — `yield { type: 'done', stopReason: finalMsg.stop_reason ?? 'end_turn' }`,必发 done chunk。
- `providers/openai-compat.ts:199` — `yield { type: 'done', stopReason: finishReason }`,必发 done chunk;finishReason 有三层 fallback(`response_metadata.finish_reason` → `additional_kwargs.finish_reason` → 基于 tool_calls 推断)。

**遗留优化点(可选,不紧急)**:两家 provider 的 stopReason 词汇表不一致 —— Anthropic 用 `end_turn / tool_use / max_tokens / stop_sequence`,OpenAI 用 `stop / tool_calls / length / content_filter`。如需上层基于 stopReason 做自动续跑策略,在 provider wrapper 层统一标准化词汇表。可放入 S-P1.1(LLMCallSession)一并处理。
