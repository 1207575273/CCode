## 0. 背景与动机

CCode 已集成 MCP（Model Context Protocol），具备「Agent <-> 外部工具」的标准化对接能力。但当前没有「Agent <-> Agent」的标准对接能力 —— SubAgent 派发只能在 CCode 进程内做，无法与外部异构 Agent（Slack Bot、企业 SaaS Agent、其他厂商 Agent）协作。

A2A（Agent-to-Agent Protocol）正是解决这个问题的开放标准，由 Google 2025-04 发布、2025-06 捐给 Linux Foundation，2026 年初发布 v1.0。生态收敛趋势是：**MCP 管工具层，A2A 管协作层**，两个都装。

本文档目标：
1. 把 A2A 协议讲清楚（速记版，详细解释见参考资料）
2. 评估它与 CCode 现有架构的契合度
3. 给出分阶段落地方案与可执行任务清单

## 1. A2A 协议速记

### 1.1 核心定位

| 维度 | A2A | MCP（对比） |
| --- | --- | --- |
| 解决问题 | Agent <-> Agent 协作 | Agent <-> 工具/数据源 |
| 调用语义 | 有状态、长生命周期 Task | 无状态 RPC |
| 对端 | 不透明的 Agent | 透明的工具 |
| 传输 | HTTP + SSE + JSON-RPC 2.0 | stdio / SSE / Streamable HTTP |
| 流式 | Task 全生命周期流（可能小时级） | 工具结果流（短） |
| 治理 | Linux Foundation | Linux Foundation AAIF |

### 1.2 三种实体

- **Message** — 轻量、无状态对话（问候、协商任务范围）。
- **Task** — 有状态、可追踪的工作单元，9 状态生命周期。
- **Artifact** — Task 的产物（文件、文本、图片）。

### 1.3 Task 生命周期（9 态）

```
submitted -> working -> ┬-> completed       (终态)
                        ├-> failed          (终态)
                        ├-> canceled        (终态)
                        ├-> rejected        (终态)
                        ├-> input_required  (中断,等用户输入)
                        ├-> auth_required   (中断,等认证)
                        └-> unknown
```

进入终态后流必须关闭。这是协议硬约束。

### 1.4 关键概念

- **AgentCard**：放在 `https://<agent>/.well-known/agent-card.json`，是 Agent 的能力说明书（name / description / skills / securitySchemes / supportedInterfaces 等）。客户端走 `createFromUrl(baseUrl)` 自动发现。
- **contextId**：跨多个 Task 的会话上下文，第一次请求由服务端生成并返回，后续请求复用。
- **JSON-RPC 核心方法**：`SendMessage` / `SendStreamingMessage` / `GetTask` / `CancelTask` / `SubscribeToTask`。
- **流式事件**：`task` / `status-update` / `artifact-update` 三类 SSE 事件。

### 1.5 生态现状（2026-05）

- 版本：v1.0
- 支持组织：150+（Google / Microsoft / AWS / Salesforce / SAP / ServiceNow / Workday / IBM）
- GitHub: 22,000+ stars
- SDK：Python / JS-TS / Java / Go / .NET 五语言生产级
- 云原生集成：Azure AI Foundry、Amazon Bedrock AgentCore、Google Cloud

## 2. 与 CCode 现状的契合度

CCode 在工具系统、事件分层、SubAgent 派发上已经构建了和 A2A 非常接近的内部抽象。下表逐项对齐：

| A2A 概念 | CCode 现有对应物 | 契合度 | 复用策略 |
| --- | --- | --- | --- |
| AgentCard | `ToolRegistry` 的工具元数据 + 配置文件 | 高 | 客户端：拉远端 AgentCard 映射成 ToolRegistry 项；服务端：从 ToolRegistry + ConfigManager 拼装 AgentCard JSON |
| Message | 内部 `Message` 类型 | 高 | message-converter 已支持多 provider 互转 |
| Task | `SubAgent` 派发任务 + JSONL 持久化 | 高 | dispatch_agent 工具的 task lifecycle 已经有 submitted/working/completed 雏形 |
| Artifact | `ToolResult` + 工具输出文件 | 中 | 需要补 artifactId / lastChunk 的概念 |
| contextId | `SessionStore` 的 sessionId | 高 | 直接映射 |
| Task 状态机 9 态 | `SubagentEvent` 的几种事件类型 | 中 | 需要补 input_required / auth_required / rejected 等中断态 |
| SSE 流式事件 | `StreamableTool.stream()` AsyncGenerator | 高 | 协议层 SSE 编码即可，业务层语义对齐 |
| JSON-RPC 端点 | 现有 `server/` Hono 实例 | 高 | 加路由即可 |
| AgentCard 发现 | `mcp-manager` 的连接逻辑 | 中 | 复用并行连接 + 单点失败降级模式 |
| 认证（bearer / OAuth2） | 现有配置系统 | 中 | 需要补 securitySchemes 协商逻辑 |

**结论**：CCode 的内部抽象与 A2A 模型高度同构，接入工作量主要在「协议编解码」和「事件状态机对齐」，业务模型几乎不动。

## 3. 接入分阶段方案

### 3.1 整体策略

按角色和工作量分四阶段：

| 阶段 | 角色 | 价值 | 工作量预估 |
| --- | --- | --- | --- |
| P0 | A2A 客户端（CCode 调用别人） | 立即可用所有公开 A2A Agent | 1-2 天 |
| P1 | 静态 AgentCard 暴露（让别人发现 CCode） | 出现在 Agent 网格里 | 0.5 天 |
| P2 | 完整 A2A Server（CCode 接受任务） | 嵌入企业 Agent 网格 | 3-5 天 |
| P3 | 双向网关 + Web Dashboard 拓扑可视化 | 形成产品差异化 | 不在本期 |

### 3.2 P0：A2A 客户端工具

新增一个内置工具 `dispatch_remote_agent`，让 LLM 能调用任意 A2A Agent。

**核心思路**：把「远端 A2A Agent」当作 CCode 的一个特殊工具 —— 比普通工具多了 Task lifecycle 和流式 artifact 增量，但接入点统一收敛到 `StreamableTool` 接口。

**文件清单**：

| 文件 | 职责 |
| --- | --- |
| `src/a2a/types.ts` | A2A 协议类型（AgentCard / Task / Artifact / 各类 Event），从 `@a2a-js/sdk` re-export 或定义子集 |
| `src/a2a/client.ts` | 封装 ClientFactory，处理 AgentCard 缓存、鉴权注入、超时重试 |
| `src/a2a/event-mapper.ts` | A2A SSE 事件 -> CCode `SubagentEvent` 映射 |
| `src/tools/agent/dispatch-remote-agent.ts` | `StreamableTool` 实现：参数（agentUrl / message / contextId?），yield 中间事件，返回最终 artifact |
| `src/config/a2a-config.ts` | 远端 Agent 注册表持久化（受信任的 AgentCard URL 白名单） |
| `tests/unit/a2a/client.test.ts` | 客户端单测（mock 远端） |
| `tests/unit/a2a/event-mapper.test.ts` | 事件映射单测 |
| `tests/unit/tools/dispatch-remote-agent.test.ts` | 工具集成单测 |

**和现有架构的对接**：

- `ToolRegistry.register(new DispatchRemoteAgentTool())`，与 `DispatchAgentTool`（本地 SubAgent）并列。
- 复用 `tool-pipeline.ts` 的 8 阶段管道，A2A 工具走和其他工具一样的权限检查 / 重复检测 / Hook / 截断。
- 复用 `SubagentEvent` 事件分层，UI 层 `SubAgent` 卡片自动能渲染（不需要新组件）。
- 复用 `repetition-detector` —— 防止 LLM 对同一个远端 Agent 反复发同样的消息。

### 3.3 P1：静态 AgentCard 暴露

只暴露能力描述，不真正接收任务。让 CCode 在 Agent 网格里可被发现。

**文件清单**：

| 文件 | 职责 |
| --- | --- |
| `src/server/a2a/agent-card-handler.ts` | GET `/.well-known/agent-card.json`，从 ToolRegistry + 配置拼装 |
| `src/server/a2a/agent-card-builder.ts` | 把 ToolRegistry 项转成 AgentCard.skills |
| `tests/unit/server/a2a/agent-card.test.ts` | 单测 |

启动参数：`--a2a-serve`（默认关闭）。

### 3.4 P2：完整 A2A Server

让 CCode 真正接受远端任务，把 AgentLoop 包装成 A2A `AgentExecutor`。

**文件清单**：

| 文件 | 职责 |
| --- | --- |
| `src/server/a2a/rpc-handler.ts` | POST `/a2a/rpc`，JSON-RPC 路由分发 |
| `src/server/a2a/sse-handler.ts` | SSE 流式响应（SendStreamingMessage / SubscribeToTask） |
| `src/server/a2a/executor-adapter.ts` | AgentLoop -> AgentExecutor 适配器，A2A 事件 <- AgentEvent 反向映射 |
| `src/server/a2a/task-store.ts` | Task 状态持久化，复用现有 libSQL 实例 |
| `src/server/a2a/auth-middleware.ts` | bearer / API key 鉴权 |
| `tests/integration/a2a/server-e2e.test.ts` | 端到端测试：本地 A2A Server + A2A Client 互通 |

**关键设计点**：
- 每个 A2A Task 起一个独立的 `AgentLoop` 实例，session 隔离。
- contextId -> sessionId 映射，contextId 复用时恢复 session。
- Task 持久化必须支持断点续传：Server 重启后客户端能 `SubscribeToTask` 恢复流。

### 3.5 P3（不在本期）

- WebSocket binding（替代 SSE，双向消息）
- Web Dashboard 加 Agent 拓扑图 + 远端 Task 监控面板
- CCode <-> CCode 互相委托（自举多 Agent 协作）

## 5. 关键设计决策

### 5.1 不引入新的事件 union，复用 SubagentEvent

理由：A2A 的 Task lifecycle 在语义上和 SubAgent 完全同构（一个长生命周期、有 status、有 artifact 的工作单元）。新建 union 会让 UI 层处理两套高度相似的事件，违反单一真源。

### 5.2 A2A Task -> CCode dispatch 工具，不是 dispatch -> A2A

也就是：A2A 是 CCode 用来调用别人的「客户端能力」，先做这一步；CCode 作为服务端接受任务（被别人调用）放 P2，因为后者要做持久化、状态机、鉴权一整套，成本高。

### 5.3 受信任 AgentCard URL 白名单 + 鉴权强制

A2A AgentCard 是 well-known 文件，理论上任何人都能伪造。LLM 不能随意发起到任意 URL 的请求 —— 必须先由用户通过 `/a2a add <url>` 显式加白名单。每个白名单条目记录鉴权方式（bearer token / API key），调用时强制注入。

这条对应 CLAUDE.md「卫语句优先」+「权限可见」原则。

### 5.4 RepetitionDetector 必须覆盖 A2A 工具

A2A 调用比本地工具慢得多（HTTP + 远端推理），LLM 反复派发同一任务的损失远大于本地工具。RepetitionDetector 阈值对 A2A 工具可以更激进（2 次 warn / 3 次 block，本地工具是 2/4）。

### 5.5 contextId 与 sessionId 的关系

P0 客户端阶段：每次 `dispatch_remote_agent` 调用产生新 contextId，不跨 CCode session 复用。简化心智模型，避免 P0 阶段陷入「跨会话共享上下文」的设计泥潭。

P2 服务端阶段再支持 contextId 复用（远端客户端传相同 contextId 时恢复 CCode session）。

## 6. 风险与未决项

| 风险 | 等级 | 缓解 |
| --- | --- | --- |
| A2A v1.0 接口变更频次 | 中 | 隔离 `src/a2a/types.ts`，升级 SDK 时只改这一层 |
| `@a2a-js/sdk` 在 Node 20+ 的兼容性 | 低 | T1 阶段先验证；不行可降级到 Python SDK + Node 调用（最差兜底） |
| 远端 Agent 不实现 cancelTask | 中 | 客户端必须本地 timeout 兜底，不依赖远端响应 cancel |
| Task 流式过程中网络断 | 中 | P0 阶段不做断线重连，由 LLM 重新发起；P2 用 `SubscribeToTask` 恢复 |
| SubAgent 黑名单是否要把 `dispatch_remote_agent` 也加进去 | 待定 | 倾向加，子 Agent 不应自主联网 |
| 是否需要 A2A 调用的费用计量 | 待定 | 远端 Agent 的 token 消耗不在 CCode 视野内，先不做，记录调用次数即可 |

## 7. 验收标准

P0 完成的硬指标：

1. `pnpm test` 全绿，新增 8 个单测文件全部通过
2. `tsc --noEmit` 无新增错误
3. 手工验证：在 CCode 里 LLM 能通过自然语言触发 `dispatch_remote_agent`，调用一个公开 A2A Agent 并拿到结果
4. `dispatch_remote_agent` 在 ToolRegistry 中正常注册，`/help` 或 `/skills` 能看到
5. `/a2a list` 能列出已配置的远端 Agent
6. 调用一个不存在的 URL 时优雅失败（不崩溃，返回 LLM 可理解的错误）
