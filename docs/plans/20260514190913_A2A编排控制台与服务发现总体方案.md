## 0. 一句话愿景

把 CCode 从「单机 CLI Agent」升级为「**带可视化控制台的 Agent 编排节点**」—— 用户给一个 HTTPS 地址，CCode 就能把对方纳入自己的 Agent 网格，在 Web 控制台里看到它、调用它、监控它、与它协作。

底层抽象不动：**对 Agent 来说，一切都是 tool 或 context**。A2A 只是把这两个抽象从「本地」扩展到「分布式」。

## 1. 产品视角：核心用户故事

### Story 1：研发人员把内部 Agent 接入 CCode

> 作为一名工程师，我刚部署了一个内部销售 Agent，地址是 `https://sales-agent.corp.example.com`。
> 我在 CCode Web 控制台点击「添加 Agent」-> 粘贴地址 -> 系统自动拉取 AgentCard -> 显示能力清单 -> 我勾选信任 -> 完成。
> 之后我在 CLI 里随便问一句「这个客户上季度成交多少」，CCode 自动识别并委托给销售 Agent，结果流式显示在终端，整个过程在 Web 端有完整的 Task 状态轨迹可回放。

**关键诉求**：服务发现要**零脚本化**——URL 一粘贴就能用，不需要写配置文件。

### Story 2：架构师查看跨 Agent 协作拓扑

> 作为一名架构师，我想知道当前 CCode 这个节点正在和哪些 Agent 通信、各 Agent 的健康状态、最近一小时的 Task 流量。
> 我打开 Web 控制台 `/agents` 页面，看到一张拓扑图：中心是 CCode，周围是 8 个外部 Agent 节点（不同颜色表示状态），节点间的连线粗细代表近期调用频次。
> 点击某个节点，右侧抽屉显示它的 AgentCard、最近 50 个 Task 的状态分布、失败率趋势图。

**关键诉求**：拓扑可视化 + 节点详情下钻 + 时间序列指标。

### Story 3：产品经理监控 Task SLA

> 作为一名 PM，我想监控一个特定的远端 Agent 是否达到 SLA。
> 我打开 `/agents/<id>/tasks`，看到一个 Task 列表（带过滤），可以筛失败的、超时的、特定 contextId 的。
> 单个 Task 点开能看到完整生命周期时间轴（submitted -> working -> ... -> completed），各阶段耗时、artifact 内容、与之关联的本地 LLM 调用。

**关键诉求**：Task 级别可观测、可回放、可关联本地行为。

### Story 4：CCode 作为被调用方

> 作为另一个 Agent 的开发者，我希望我的 Agent 能委托 CCode 帮我写代码。
> 我读 CCode 的 `https://my-ccode.example.com/.well-known/agent-card.json`，看到能力清单（编辑文件、运行 bash、做代码审查等），通过 A2A 协议调用 -> CCode 在后台跑一个 AgentLoop -> 把 artifact 流式回传。

**关键诉求**：CCode 自身是一等公民的 A2A Server。

### Story 5：单机多 CCode 实例互相编排（v2.1 新增）

> 作为一名工程师，我在笔记本上同时开了两个项目：A 项目是 Python 数据流水线，B 项目是 React 前端。每个项目目录都跑了独立的 CCode 实例（不同进程、不同端口）。
> B 项目我想让 Agent 写一个调用 A 项目数据接口的 mock，A 项目的 CCode 显然对那套数据更熟。
> B 的 Web 控制台右下角弹 Toast：「检测到本机 CCode 实例 `~/work/data-pipeline` (PID 12345, port 9801)，是否加入网格？」
> 我点「加入」——无需粘贴 URL、无需输入 Token（本机受信）——秒级纳管。之后 B 的 LLM 在分析需求时自动把数据接口部分委托给 A。

**关键诉求**：零配置发现 + 一键加入 + 本机进程默认受信但可移除。

### Story 6：跨机器配置导入导出（v2.1 新增）

> 我在公司笔记本上配好了 12 个常用 Agent（公司内部 + 第三方公开）。周末打开家里台式机，想把这套配置带过来。
> 我在公司笔记本 Web 控制台 `/agents` 页右上角点「导出」-> 下载 `ccode-agents-export-20260514.json`。
> 文件结构清晰：Agent 元数据完整，但所有 token / secret 字段被替换成 `"__SECRET_PLACEHOLDER__"`。
> 家里电脑上点「导入」-> 上传文件 -> 预览列表显示 12 个待激活 Agent，其中 4 个标注「需要补 token 才能启用」。
> 我逐个补完，启用。

**关键诉求**：易导出、易导入、secrets 绝不外泄、明确提示缺什么。

| 列表视图 | 表格：name / endpoint / status / 24h calls / avg latency / last seen / actions | 复用 Tailwind 表格类 |

### 2.5 「Task 详情」页设计要点

时间轴风格，从上到下：

```
[time]  TASK CREATED        contextId: ctx-abc
        |
[time]  -> working           reason: "fetching data"
        |
[time]  -> artifact-update   artifact: report.txt (3.2 KB)
        |  [展开看内容]
        |
[time]  -> input_required    message: "Need confirmation"
        |  [中断,等用户输入,右侧操作区可继续]
        |
[time]  -> working
        |
[time]  -> completed         duration: 47.3s | tokens: 8421
```

每个节点可展开看原始 JSON。底部关联本地 LLM 调用（如果 Task 是由 CCode 内 LLM 触发的，能看到触发它的 user message 和 LLM tool_call）。

### 3.2 三层接入角色（v1 文档的延续 + 扩展）

| 阶段 | 角色 | 出站 | 入站 | Web 可见 |
| --- | --- | --- | --- | --- |
| M1 | 客户端 | dispatch_remote_agent 工具 | 不接收 | 列表 + 单 Task 查看 |

| M4 | 编排节点 | 多 Agent Saga | 同上 | 跨 Agent 流程编排 UI |

### 3.3 关键架构原则

**KP-1：Agent 注册表是唯一真源**
所有 Agent 信息（包括 CCode 自己）都存在 libSQL 的 `agent_registry` 表，Web 和 CLI 都从同一份数据读，不在前端做内存状态。

**KP-2：A2A 事件独立 union，UI 组件复用（v2.2 修订）**
~~原方案：直接复用 SubagentEvent~~ —— 经核查 `src/core/agent-events.ts:97-121`，SubagentEvent 仅 spawn/progress/done 三态，无法承载 A2A 9 态机（含 input_required / auth_required / rejected）和 artifact 增量。
新决策：**事件 union 与 SubagentEvent 平级独立**（命名 `A2AEvent`），但 **UI 组件层复用** —— SubAgentCard / SubAgentDrawer 通过适配器 hook（`useUnifiedAgentCardProps`）接受两种事件源，统一渲染折叠卡片 + 时间轴。

**KP-3：Bridge 不解析 A2A 协议**
Bridge 继续做哑路由器，A2A 协议的 JSON-RPC 解析、SSE 编码、状态机推进全部在 dashboard/a2a/ 模块里完成。

**KP-4：Web 端通过 REST 操作，通过 WS 接收推送**
- 添加 Agent / 删除 / 测试连通性 -> REST POST
- Task 状态变化 / artifact 增量 -> WS 推送 `a2a_event`
分工和现有架构对齐。

**KP-5：服务发现是「拉取 + 信任」两步**
拉取 AgentCard 不等于信任。必须用户在 Web 端显式点「信任并启用」，才会写入 trusted 表，LLM 才能调用。这是安全底线。

**KP-6：HTTP 接口规范——禁用 PUT/DELETE/PATCH（v2.2 措辞澄清）**
项目硬规：所有 `/api/*` 和 `/a2a/*` 路由只用 **GET 和 POST**，禁用 PUT / DELETE / PATCH。
- GET：纯查询，幂等，无副作用
- POST：所有写操作（创建 / 修改 / 删除 / 调用动作）统一走 POST
- **允许 `:id` 等路径参数作为资源标识**；写操作 URL 末尾用动词，例如 `POST /agents/:id/delete`、`POST /agents/:id/update`、`POST /tasks/:id/cancel`
理由：CDN / 反向代理 / 部分防火墙对 PUT/DELETE 处理不一致；简化客户端封装；与现有 dashboard/api.ts 风格统一。

**KP-7：本机实例发现走 lockfile，不走网络广播**
本机多 CCode 实例发现机制基于 `<homedir>/.ccode/instances/<pid>.json` 共享目录（Node 内用 `path.join(os.homedir(), '.ccode/instances/')` 拼出，`~` 不会被自动展开），不用 mDNS、Bonjour、TCP 广播。理由：跨平台稳定（Windows mDNS 弱）+ 不触发杀毒告警 + 文件系统是天然受信任域。

**KP-8：A2A 反向回调走单次过期 callback_token（v2.2 新增）**
M3 阶段 CCode 作为 Server 接收远端 Agent 任务，**任务执行中如果 CCode 需要反向调用远端 Agent 的另一个能力（典型场景：远端 A 委托 CCode 执行代码任务，CCode 中途需要查 A 上的日志）**，A 必须能验证回调身份。
机制：A 发任务给 CCode 时，在消息头附带 `x-callback-token`（单次有效、5 分钟过期、绑定 taskId 和 agent_chain）。CCode 反向回调时必须带回该 token；A 校验通过后允许此次反向调用，token 即作废。Token 在双方 libSQL 短存 5 分钟即清。

**KP-9：跨 Agent 调用链 call_chain 防循环（v2.2 新增）**
A2A 消息头必须携带 `x-a2a-call-chain: ["agent-A-uuid", "agent-B-uuid"]`，每个 Agent 收到时：
- 自检 `agent_chain.includes(self.id)` -> 是则立即返回 `state: 'rejected'`，reason='circular-call-detected'
- 否则把自己 append 到链尾再向下游传播
- 链最大长度 8（深度上限）；超出也 reject
依据：进程内 RepetitionDetector 解决不了跨进程/跨主机的循环调用，必须在协议层挂 trace 链。

## 4. 数据模型（libSQL 新增表）

### 4.1 agent_registry

```sql
CREATE TABLE agent_registry (
  id                TEXT PRIMARY KEY,       -- uuid
  url               TEXT NOT NULL UNIQUE,   -- AgentCard 发现 URL（baseUrl）
  name              TEXT NOT NULL,          -- 从 AgentCard.name 同步
  alias             TEXT,                   -- 用户起的别名（v2.1）
  description       TEXT,
  agent_card_json   TEXT NOT NULL,          -- 完整 AgentCard 快照
  capabilities      TEXT,                   -- skills 提取的简化 JSON 数组
  security_scheme   TEXT,                   -- bearer / apikey / oauth2 / none
  auth_secret_ref   TEXT,                   -- 引用 secrets 表，不直接存 token
  status            TEXT NOT NULL,          -- 'trusted' / 'pending' / 'disabled' / 'unreachable'
  kind              TEXT NOT NULL,          -- 'remote' / 'local-instance' / 'imported' (v2.1)
  discovery_source  TEXT NOT NULL,          -- 'manual' / 'auto-local' / 'imported' (v2.1)
  local_instance_id TEXT,                   -- 关联 local_instances.id (仅 kind=local-instance)
  last_seen_at      INTEGER,                -- 最近一次健康检查通过时间
  last_error        TEXT,                   -- 最近一次连接错误
  protocol_version  TEXT,                   -- AgentCard.protocolVersion 快照（v2.2,用于版本协商）
  deleted_at        INTEGER,                -- 软删除时间戳（v2.2,NULL 表示未删除）
  created_at        INTEGER NOT NULL,
  updated_at        INTEGER NOT NULL
);
CREATE INDEX idx_agent_registry_status ON agent_registry(status) WHERE deleted_at IS NULL;
CREATE INDEX idx_agent_registry_kind ON agent_registry(kind) WHERE deleted_at IS NULL;
```

**为什么软删除（v2.2）**：删除 Agent 时如果硬删除，关联的 a2a_tasks / a2a_task_events 会变成孤儿。软删除让 Task 历史可追溯（Task 详情页仍能显示已下线的 Agent 名），同时新查询自动过滤（部分索引 + WHERE 子句）。

### 4.2 a2a_tasks

```sql
CREATE TABLE a2a_tasks (
  id                   TEXT PRIMARY KEY,    -- A2A taskId
  agent_id             TEXT NOT NULL,       -- 关联 agent_registry.id
  context_id           TEXT NOT NULL,       -- A2A contextId
  session_id           TEXT,                -- 关联 CCode 内部 sessionId（如有）
  parent_tool_call_id  TEXT,                -- v2.2 关联触发该 Task 的本地 toolCall(outbound 才有)
  direction            TEXT NOT NULL,       -- 'outbound'(CCode 调用别人) / 'inbound'(别人调 CCode)
  state                TEXT NOT NULL,       -- TaskState 9 态
  initial_message_ref  INTEGER,             -- v2.2 引用 a2a_task_events 第一条 event id(初始 message 体放事件流避免大字段)
  initial_message_text TEXT NOT NULL,       -- 摘要(前 4KB),完整体走 events 表
  artifacts_json       TEXT,                -- 产物列表 JSON 摘要(每条 artifact 含 artifactId + name + size)
  total_tokens         INTEGER DEFAULT 0,   -- 本地 LLM 关联消耗（仅 inbound 有意义）
  cost_amount          REAL,                -- v2.2 该 Task 成本(初期可 NULL,M3 接入计量后填充)
  cost_currency        TEXT,                -- v2.2 'USD' / 'CNY' 等
  error_code           TEXT,                -- v2.2 终态为 failed/rejected 时的错误码
  error_message        TEXT,                -- v2.2 错误描述(脱敏后)
  duration_ms          INTEGER,             -- submitted -> 终态 总耗时
  call_chain_json      TEXT,                -- v2.2 调用链 JSON 数组,见 KP-9
  created_at           INTEGER NOT NULL,
  updated_at           INTEGER NOT NULL,
  ended_at             INTEGER
);
CREATE INDEX idx_a2a_tasks_agent_state ON a2a_tasks(agent_id, state);
CREATE INDEX idx_a2a_tasks_context ON a2a_tasks(context_id);
CREATE INDEX idx_a2a_tasks_session ON a2a_tasks(session_id);
CREATE INDEX idx_a2a_tasks_list ON a2a_tasks(direction, state, created_at DESC);  -- v2.2 列表页主查询路径
CREATE INDEX idx_a2a_tasks_parent_tool ON a2a_tasks(parent_tool_call_id);          -- v2.2
```

**为什么拆 `initial_message_text` + `_ref`（v2.2）**：A2A message 可能内嵌大图片 base64 或长文本（10MB+），直接写主表会让所有 Task 列表查询变慢。摘要进主表（4KB 截断），完整体走 a2a_task_events 第一行。Task 详情页才 join 取全文。

### 4.3 a2a_task_events

```sql
CREATE TABLE a2a_task_events (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id     TEXT NOT NULL,                -- 关联 a2a_tasks.id
  kind        TEXT NOT NULL,                -- 'task' / 'status-update' / 'artifact-update' / 'message'
```

### 4.4 local_instances（v2.1 新增，v2.2 修订）

本机活跃 CCode 实例的影子表。lockfile 是真源（写在 `<homedir>/.ccode/instances/`），libSQL 表是缓存 + 关联用：

```sql
CREATE TABLE local_instances (
  id                TEXT PRIMARY KEY,    -- v2.3 直接使用 lockfile.instanceId(uuid-v4)
```

**索引修订（v2.3）**：~~原 v2.2 单列 `UNIQUE(agent_card_url)` 选错~~ — `agent_card_url=http://127.0.0.1:<port>/.well-known/...` 不含 pid，**端口被回收复用就会撞 UNIQUE**。改用复合索引 `UNIQUE(agent_card_url, started_at)`，startedAt 单调递增天然不撞；同时主键 `local_instances.id` 直接复用 lockfile.instanceId（uuid-v4），upsert 时按 instanceId 查找最稳。

**新增隔离字段（v2.2）**：`hostname + os_user` 字段防 WSL / Windows 双写、Docker 容器映射 /home、多用户登录等场景的幽灵实例 — scanner 扫描时只看本 hostname + 本 os_user 的 lockfile。

### 4.5 lockfile 文件设计（v2.1 新增，v2.2 修订）

每个 CCode 实例启动 Web Server 成功后写入 `<homedir>/.ccode/instances/<pid>.json`（Node 代码用 `path.join(os.homedir(), '.ccode/instances/', pid+'.json')`）：

```json
{
  "schema": "ccode-instance-lock/v1",
  "pid": 12345,
  "port": 9801,
  "agentCardUrl": "http://127.0.0.1:9801/.well-known/agent-card.json",
  "projectPath": "/Users/me/work/data-pipeline",
  "sessionId": "ccode-abc-xyz",
  "version": "0.13.0",
  "startedAt": "2026-05-14T19:00:00Z",
  "lastHeartbeat": "2026-05-14T19:00:30Z",
  "hostname": "MacBook-Pro.local",
  "osUser": "me",
  "instanceId": "uuid-v4-generated-once-at-start"
}
```

**生命周期（v2.2 修订）**：
- 写入：bootstrap 启动 Bridge Server 成功后，原子写（`<pid>.json.tmp` -> rename）
- 心跳：每 10 秒重写 `lastHeartbeat` 字段（同样原子写）
- 优雅删除：`process.on('exit')` / `SIGINT` / `SIGTERM` 三钩子注册 unlink
- 非优雅退出兜底（SIGKILL / 断电 / OOM）：scanner 双判
  - 判定 1：`Date.now() - lastHeartbeat > 30s`（心跳过期）
  - 判定 2：`process.kill(pid, 0)` 抛 `ESRCH`（进程不存在）
  - 任一为真即清理 lockfile + 标记 dismissed
- **Windows 行为差异**：`process.kill(pid, 0)` 在 Win 上对非本用户进程会抛 `EPERM`，scanner 必须**区分 ESRCH（已死）vs EPERM（视为存活）**，避免误杀合法 lockfile
- PID 复用兜底：lockfile 内 `startedAt` 与缓存表对比，不一致视为新实例；`instanceId` 字段提供二次锚定

### 4.6 secrets 表（v2.2 新增）

**为什么必须有**：评审发现原方案 §4.1 引用了不存在的 secrets 表。鉴权 token 不能裸存进 agent_registry，否则 SQL 全文搜索、误导出都会泄露。

```sql
CREATE TABLE secrets (
  id              TEXT PRIMARY KEY,    -- uuid,被 agent_registry.auth_secret_ref 引用
  scope           TEXT NOT NULL,       -- 'agent' / 'callback' / 'reserved'
  scope_ref_id    TEXT NOT NULL,       -- 对 scope='agent' 即 agent_registry.id
  cipher_value    BLOB NOT NULL,       -- 加密后的 token 字节流
  iv              BLOB NOT NULL,       -- 加密 IV(AES-256-GCM 用)
  algorithm       TEXT NOT NULL,       -- 'aes-256-gcm' / 'obfuscation-v1'(M2 弱加密)
  key_ref         TEXT NOT NULL,       -- key 来源标识: 'machine-id-derived' / 'os-keychain://service/account'
  created_at      INTEGER NOT NULL,
  updated_at      INTEGER NOT NULL,
  expires_at      INTEGER              -- 仅 callback token 用,绝对过期时间
);
CREATE INDEX idx_secrets_scope ON secrets(scope, scope_ref_id);
CREATE INDEX idx_secrets_expires ON secrets(expires_at) WHERE expires_at IS NOT NULL;
```

**加密策略阶段化**：
- **M2 阶段**：用 `obfuscation-v1` —— 派生 key 来源是 `hash(machine-id + lockfile-instance-uuid)`，AES-256-GCM 加密。不是真正的安全（同机器同用户可解），但挡住「误导出」「SQL 全文 grep」「bug 把 token 打 log」三类常见泄露。
- **M3 阶段**：升级到 OS keychain（macOS Keychain / Windows Credential Manager / linux-keyring），`key_ref` 字段保留接入路径。

**callback_token 用 scope='callback'**（见 KP-8）：5 分钟绝对过期，scanner 定期清理 `expires_at < now()` 的行。

**事件 union 独立、路由分层**。两条变化：

**(1) A2AEvent 与 SubagentEvent 平级独立**（评审 B-2）。UI 组件层通过适配器复用，事件类型不混淆：

```ts
type A2AEvent =
  | { type: 'a2a_task_created';  task: A2ATaskSnapshot }
  | { type: 'a2a_task_status';   taskId: string; state: TaskState; message?: string; ts: number }
  | { type: 'a2a_task_artifact'; taskId: string; artifact: Artifact; lastChunk: boolean; ts: number }
  | { type: 'a2a_task_ended';    taskId: string; state: 'completed'|'failed'|'canceled'|'rejected'; duration_ms: number; ts: number }
  | { type: 'a2a_task_input_required'; taskId: string; prompt: string; ts: number }   // 中断态需用户输入
```

**(2) Bridge 推送加 scope 二元路由**（评审 B-1）。现有 `routeMessage` 是 per-session 路由，但 A2A 全局事件不属于任何 session：

```ts

type BridgePushEnvelope = {
  scope: 'session' | 'node'   // session: 现有逻辑,只发同 sessionId 的 Web; node: 节点全局,发所有 Web 客户端
  sessionId?: string           // scope='session' 时必填
  event: BusinessEvent | SubagentEvent | A2AEvent | ObservabilityEvent
}
```

**Scope 分配规则**：
- `a2a_task_*` 事件 → `scope='session'`（关联到触发它的 CLI session）
- `a2a_agent_status` / `a2a_topology_update` / `local_instance_*` → `scope='node'`（与 session 无关）
- 现有 BusinessEvent / SubagentEvent 默认 `scope='session'`，不破坏现有行为

Bridge `routeMessage` 增加分支：scope='node' 时直接 `broadcastToClients(envelope, clientType='web')` 不查 sessionId 映射。

### 5.5 本机实例扫描 worker（v2.1 新增，v2.2 重写）

新增 worker `src/a2a/instance-scanner.ts`：

```ts
import { join } from 'node:path'
import { homedir, hostname, userInfo } from 'node:os'

const INSTANCE_DIR = join(homedir(), '.ccode/instances')   // 永远不用 '~',Node 不展开
const HOST = hostname()
const OS_USER = userInfo().username

// 启动时机：bootstrap 启动 Bridge Server 后立即开 + 写自己的 lockfile + 启心跳定时器(10s)
// 扫描频率：30 秒一次
// 文件 watch：用 fs.watch 监听 INSTANCE_DIR,新文件立即响应

async function scanOnce() {
  const files = await listLockfiles(INSTANCE_DIR)
  for (const f of files) {
    const lock = await readLockfile(f)
    if (lock.pid === process.pid) continue                              // 跳过自己
    if (lock.hostname !== HOST || lock.osUser !== OS_USER) continue     // v2.2 跨主机/跨用户隔离

    if (isDead(lock)) {
      await unlink(f).catch(() => {})                                   // 文件可能已被别人清掉
      await markLocalInstanceDismissed(lock)
      emit({ scope: 'node', event: { type: 'local_instance_lost', instanceId: lock.instanceId } })
      continue
    }
    const isNewlyDiscovered = await upsertLocalInstance(lock)
    if (isNewlyDiscovered) {
      emit({ scope: 'node', event: { type: 'local_instance_discovered', instance: snapshot(lock) } })
    }
  }
}

// v2.2 重写: 双判 + 区分 ESRCH/EPERM
function isDead(lock: Lockfile): boolean {
  // 判定 1: 心跳过期 30s
  const heartbeatStale = Date.now() - new Date(lock.lastHeartbeat).getTime() > 30_000
  // 判定 2: 进程检测
  let processDead = false
  try {
    process.kill(lock.pid, 0)
    // 成功 = 进程存在
  } catch (e: any) {
    if (e.code === 'ESRCH') processDead = true       // 进程不存在
    else if (e.code === 'EPERM') processDead = false  // Windows 权限错: 视为存活(可能是别用户进程,不要误杀)
    else processDead = false                          // 其他错误保守视为存活
  }
  return heartbeatStale && processDead   // 双判合取: 必须同时心跳过期 + 进程不存在,才视为死亡
}
```

**关键纪律（v2.2 修订）**：
- **双判**：心跳过期 30s **AND** `kill(pid,0)` 返回 ESRCH —— 必须同时满足才清理，避免任一判定单边漏判
- **Windows 行为兜底**：`kill(pid, 0)` 在 Win 上对非本用户/系统进程抛 `EPERM`，必须**视为存活**而非视为死亡（否则误杀合法 lockfile）
- **跨主机/跨用户隔离**：scanner 只看 hostname + osUser 都匹配的 lockfile，防 WSL/Win 双写、Docker 映射 /home、多用户登录幽灵
- **路径不用 `~`**：始终 `path.join(os.homedir(), '.ccode/instances/')` 拼出
- **原子写**：lockfile 写入和心跳更新都走 `<pid>.json.tmp` -> `rename` 两步
- **Toast 风暴 debounce**：emitter 内 5 秒窗口聚合，同一窗口内多个 `local_instance_discovered` 合并为一条带计数的事件（前端 Toast 显示"3 个新实例待加入"）

```
   [前端展示 AgentCard: 名字 / 描述 / 能力清单 / 鉴权要求]
            |
            v

            v
```

## 7. 状态同步与一致性

### 7.1 Web 端如何感知 CLI 触发的 A2A 调用

LLM 在 CLI 端调用 `dispatch_remote_agent` -> 工具内部走完整 A2A 流程 -> 同时把每个阶段写入 a2a_tasks / a2a_task_events，并通过 EventBus 推送 a2a_* 事件 -> Bridge 转发给 Web -> Web 拓扑图的对应节点闪烁高亮。

**关键纪律**：A2A 工具的实现里，**写库 + 推事件**必须同步完成，不能只推不写或只写不推。最佳做法是封装一个 `A2AEventEmitter`，内部先写 libSQL 再 emit，单一真源。

### 7.2 Web 端如何主动取消 CLI 进行中的 A2A Task

```
Web 点「取消」 -> POST /api/a2a/tasks/:id/cancel
                     |
                     v
          dashboard 通过 EventBus 发 cancel 信号 -> 找到对应工具的 AbortController -> abort
                     |
                     v
          dispatch_remote_agent 收到 abort -> 调用 A2A client.cancelTask()
                     |
                     v
          A2A 服务端响应 canceled -> 写库 + 推 a2a_task_ended
                     |
                     v
          所有 Web 端同步收到
```

### 7.3 CLI 离线时 Web 怎么办

Web 是观察者。CLI 离线时：
- Agent 列表照常显示（数据来自 libSQL）
- 拓扑图所有节点显示为 `offline`
- 添加 / 删除 Agent 仍可用（直接写库，CLI 上线后自动加载）
- 不能调用 / 取消 Task（弹 Toast 提示「需要 CLI 在线」）

### 7.4 本机多实例的状态同步（v2.1）

**场景 A：实例 B 启动**
1. B 写自己的 lockfile -> B 自己的 scanner 也扫到自己（跳过）
2. A 的 scanner 30s 内（或 fs.watch 立即）扫到 B 的 lockfile
3. A 推 `local_instance_discovered` 事件 -> A 的 Web 端 Toast 提醒
4. 反向同理：B 的 scanner 扫到 A，B 的 Web 端也 Toast

**场景 B：实例 B 正常关闭**
1. B 的 exit hook 删除 lockfile
2. A 的 scanner 下一轮发现 lockfile 消失 -> 推 `local_instance_lost` 事件
3. A 的 Web 端：拓扑图节点变灰 + 列表项标 "已离线"
4. 如果 A 已经把 B 加入了 agent_registry（status='trusted'），保留记录但 status 改 'unreachable'

**场景 C：实例 B 异常崩溃**
1. lockfile 没被删除（孤儿）
2. A 的 scanner 通过 `process.kill(B.pid, 0)` 检测 -> 抛错 -> 判定 B 已死
3. A 主动删除孤儿 lockfile
4. 后续与场景 B 一致

**场景 D：实例 B 重启（同项目同目录）**
1. B 新进程 PID 可能复用之前的 PID（极少见但可能）
2. A 用 lockfile.startedAt 时间戳对比 local_instances 缓存
3. startedAt 更新 -> 视为新实例（旧记录归档，新记录创建）

**场景 E：用户在 A 上把 B 移除**
1. A POST `/api/a2a/agents/<bId>/delete` -> 从 agent_registry 删除
2. 但 B 的 lockfile 仍在 -> A 的 scanner 下次扫描会再次发现
3. 解决：删除时同步把 local_instances.status 设为 'dismissed'，scanner 跳过 dismissed
4. 用户想重新加入：在「本机实例」Tab 手动「解除忽略」

### 7.5 WS 重连与事件 catch-up（v2.2 新增）

**问题**：A2A Task 可能小时级运行，期间用户切换浏览器 tab、休眠笔记本、网络抖动都会导致 WS 断开。浏览器重连后如果丢失中间事件，前端状态机会停在断点（明明 Task 已完成，UI 仍显示 working）。

**机制**：
1. WS 客户端在每次成功收到事件时记录 `lastEventTs`（精确到毫秒）到 in-memory + sessionStorage
2. WS 重连后第一条消息发 `{ type: 'register', clientType: 'web', sessionId, lastEventTs }`
3. Bridge 收到带 `lastEventTs` 的 register 后：
   - **session 域 catch-up**：从 SessionStore 读该 sessionId 自 lastEventTs 后的事件，推送给 Web
   - **node 域 catch-up**：从 libSQL 读 a2a_task_events 中所有 `ts > lastEventTs` 的事件，按 Task 分组推送
4. Web 端逐条 apply 事件到状态机；apply 完成后切回实时模式
5. 单 Task 视图额外有兜底：`GET /api/a2a/tasks/:id/events?since=<lastEventTs>` 主动拉增量，作为 WS 失败时的降级方案

**边界**：
- `lastEventTs` 超过 24h 视为过期，强制走全量 `GET /api/a2a/tasks/:id` 重建状态
- WS catch-up 单次推送 > 500 条时改走 REST 增量拉取（防 WS 帧风暴）
- a2a_task_events 是 append-only，ts 单调递增，按 ts 索引查询性能稳定

## 9. 关键设计决策与权衡

| ID | 决策 | 取舍 |
| --- | --- | --- |
| D-1 | Agent 注册表存 libSQL 而不是 JSON 文件 | 写表麻烦但 Web/CLI 共享数据零成本，多进程安全 |
| D-2 | Web 端不引入 Zustand/Redux，保持 hooks + WS 推送 | 与现有架构一致，缺点是跨页面共享 Agent 状态稍麻烦，用 useContext 兜底 |
| D-3 | 引入 ReactFlow（新依赖） | 拓扑图工作量减少 70%，bundle 增加 50KB，可接受 |
| D-4 | A2A 事件 union 独立，UI 组件复用（v2.2 修订）| 原方案"复用 SubagentEvent"经核查不成立（SubagentEvent 仅 3 态，A2A 9 态机塞不进去）。改为 union 拆分 + 通过适配器 hook 让 SubAgentCard/SubAgentDrawer 渲染两类 |
| D-5 | 服务发现分「拉取」与「信任」两步 | 安全优先，多一步点击换来不被 LLM 误调用陌生 Agent |
| D-6 | 鉴权 token 不直接存 agent_registry，引用 secrets 表 | secrets 表预留给后续 OS keychain 集成，避免 SQL 全文搜索泄露 |
| D-7 | A2A 工具的 RepetitionDetector 阈值更激进（2 warn / 3 block） | 远端调用成本高，对弱模型多防一层 |
| D-8 | Bridge 不解析 A2A 协议，保持哑路由 | 协议升级时 Bridge 不需改，单一职责 |
| D-9 | contextId 在 M1/M2 不跨 CCode session 复用 | 简化心智模型，M3 服务端再处理跨会话 |
| D-10 | 健康检查 30s 一轮，不做心跳长连接 | 实现简单，对生产可接受；后续可升级为 SSE 心跳 |
| D-11 | 本机实例发现用 lockfile 不用 mDNS（v2.1） | mDNS 在 Windows 不稳定且触发杀软告警；lockfile 跨平台稳、文件系统是天然受信任域 |
| D-12 | secrets 导出强制脱敏，不提供「明文导出」选项（v2.1） | 导出文件极易进 Git / 邮件 / 云盘；明文 token 泄露不可控；导入时多一步换安全 |
| D-13 | PID 存活检查用 Node `process.kill(pid, 0)`（v2.1） | 原生跨平台 API，无需调用 tasklist / ps；PID 复用靠 startedAt 时间戳辅助识别 |
| D-14 | HTTP 接口规范禁用 PUT/DELETE/PATCH（v2.2 措辞澄清）| 允许 `:id` 路径参数；写操作 URL 末尾用动词（`/agents/:id/delete`）；CDN / 反向代理兼容性最佳；与现有 dashboard/api.ts 统一 |
| D-15 | 本机实例加入时 securityScheme='hmac-machine-id'（v2.2 修订，v2.3 细化）| ~~原方案默认 securityScheme='none' 在企业多用户机器是漏洞~~。新决策：默认走 HMAC(machine-id + instanceId) 校验。**HMAC 由 CCode 程序自动派生 + 自动握手,用户全程无感知**(与 Story 5 "无需粘 Token,秒级纳管" 产品承诺一致 — 用户感知的是零摩擦,HMAC 是程序底层防同机器其他用户)。**machine-id 派生路径选型(v2.3)**:自写跨平台读取(Win 读 `HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid`、Linux 读 `/etc/machine-id`、macOS 调 `ioreg` 取 IOPlatformUUID),约 30 行代码,WSL 边界单独处理(读 `/etc/machine-id` 即可,不读 Win 注册表)。不引外部依赖(`node-machine-id` 最近更新 2019,弃用风险)。chmod 600 lockfile 是 M2b 任务前置(防同机器其他用户读 instanceId 后伪造 HMAC);单用户机器可在配置关闭走 'none'。 |
| D-16 | A2A 反向回调用单次 callback_token（v2.2 新增，对应 KP-8）| token 5 分钟过期、绑定 taskId 和 call_chain、5 分钟内单次有效；libSQL secrets 表 scope='callback' 存储；scanner 定期清理过期 |
| D-17 | 跨 Agent 调用链 call_chain 防循环（v2.2 新增，对应 KP-9）| A2A 消息头携带 agent_chain JSON 数组；每个 Agent 收到时检查自己是否已在链中,是则 reject；最大深度 8 |
| D-18 | a2a_tasks initial_message 拆 ref + text 摘要（v2.2）| 防大字段拖慢列表查询；摘要进主表 4KB 截断，全文走 events 表 |
| D-19 | secrets M2 用 obfuscation-v1, M3 升级 OS keychain（v2.2）| obfuscation 不是真安全但挡住误导出/SQL grep/日志泄露三类常见风险；algorithm + key_ref 字段为升级铺路 |
| D-20 | Agent 删除走软删（v2.2）| 硬删会让 a2a_tasks/events 变孤儿，Task 详情页查不到 Agent 名；软删 + 部分索引 WHERE deleted_at IS NULL 兼顾历史可追溯和查询性能 |

## 10. 风险与未决

| 风险 | 等级 | 缓解 |
| --- | --- | --- |
| A2A v1.0 spec 仍可能小幅变更 | 中 | 隔离 `src/a2a/types.ts`，升级 SDK 时只改这一层 |
| ReactFlow 与 React 19 严格模式兼容性 | 中 | M2 第一天先验证 demo |
| 拓扑图节点 > 50 时性能 | 低 | 加聚类（按 capability 分组）+ 懒加载边详情 |
| Web 端鉴权 token 输入泄露风险 | 高 | Token 不回显，仅显示 mask；存储用 secrets 表抽象 |
| 远端 Agent 不实现 cancelTask | 中 | 客户端本地 timeout 兜底，不依赖远端响应 |
| 多 CCode 实例同时访问 libSQL 写冲突 | 低 | 现有架构是单实例，未来多实例时再加分布式锁 |
| CCode 作为 Server 被滥用（DDoS） | 中（M3 阶段） | 鉴权 + 限流中间件 + IP 白名单 |
| AgentCard 拉取超时阻塞 UI | 低 | 前端 8s 超时 + 友好错误 |
| 数据库迁移失败回滚 | 中 | 迁移脚本必须事务化，失败保留旧表数据 |
| 待定：是否支持 WebSocket binding | 待定 | M3 阶段决定，SSE 已足够，WS 是未来优化 |
| lockfile 孤儿堆积（崩溃未删）| 低（v2.1） | scanner 每 30s 检查 PID 存活并清理；用户也可手动删 `~/.ccode/instances/` |
| PID 复用误判 / Windows EPERM 误判 | 中（v2.2 升级）| ESRCH/EPERM 分流处理（EPERM 视为存活）；心跳 + kill 双判合取；instanceId 二次锚定 |
| lockfile 多进程并发写竞争 | 极低（v2.1） | 文件名带 PID 天然唯一；写入用 `.tmp` + rename 原子化 |
| 导入恶意 JSON 文件 | 中（v2.1） | schema 严格校验 + URL 协议白名单（http/https only）+ 用户必须逐项确认 |
| 跨机器导出文件版本不兼容 | 低（v2.1） | schema 字段含 `"ccode-agents-export/v1"`，不兼容明确报错 |
| 本机实例之间循环调用 | 中（v2.1） | RepetitionDetector 已覆盖；SubAgent 黑名单可选包含 dispatch_remote_agent |

### 14.4 已识别但优先级靠后的盲点（M2 实施时关注，不修可活）

1. **健康检查 30s 一轮 vs Task 实时事件的最终一致性窗口**：节点显示 offline 但 Task 还在更新,UX 抖动。
   - 缓解:设 60s 宽限期 + 2 轮 fail 才标 offline;或 Task 实时事件反向更新 `last_seen_at`(把 Task 活动视为隐式 health 信号)。

2. **多 Tab BroadcastChannel 同时 catch-up 重复**：两个 Web Tab 都断网 -> 都重连 -> 都发 register{lastEventTs} -> Bridge 给两份完整 catch-up,node 域事件每 Tab 收两遍。
   - 缓解:BroadcastChannel leader 选举(first tab wins);或与 N-6 联动按 eventId 去重让重复 apply 幂等。

3. **scanner 清理孤儿时未联动 agent_registry.status**：lockfile 已清但 agent_registry 里 kind='local-instance' 仍 status='trusted',LLM 仍能尝试 dispatch 到已死实例。
   - 缓解:scanner 清孤儿时同步把 agent_registry 对应记录 status 改 'unreachable'。

4. **进程崩溃后 a2a_task_events 已入库但 emit 丢失**：依赖 Web 用 lastEventTs 自驱拉补即可(与 N-5 不变量联动,先写库后 emit)。
   - 缓解:本项依赖 N-5 落地即自动解决,不需要额外处理。

5. **secrets `algorithm` 字段无 CHECK 约束限定取值**：未来字段值漂移(如笔误写成 'aes256gcm')无报错。
   - 缓解:在写入代码侧强制 `algorithm ∈ {'obfuscation-v1','aes-256-gcm'}` 枚举校验。

6. **`a2a_tasks.cost_amount` / `cost_currency` 缺索引**：PM 想做"按月按币种 TOP 成本 Agent 排行" 会扫全表。
   - 缓解:M3 接入成本计量时补 `idx_a2a_tasks_cost ON a2a_tasks(cost_currency, created_at)`。
