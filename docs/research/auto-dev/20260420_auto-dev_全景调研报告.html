01一句话定位与核心价值

AutoDev 3.0 Xiuper 不是 Cursor 的开源替代,也不是 Claude Code 的加强版; 它的本质是 "AI 工具联邦的客户端与宿主"—— 用统一的 Agent 引擎 + 开放生态协议(MCP / AGENTS.md / Claude Skill / SpecKit / A2A), 把需求、编码、审查、数据、原型、Web 交互这 6 个开发阶段串进一条工作流, 再通过 Kotlin Multiplatform 把这条工作流投送到开发者所在的任何一个屏幕上。

口号: One Platform. All Phases. Every Device. — 统一平台 · 全开发阶段 · 跨全设备。

04引擎骨架与分层架构

引擎核心是 CodingAgentExecutor(714 行)维持 LLM → 解析 → 执行工具 → 回环 的多轮循环。一切外部事件都通过 CodingAgentRenderer 接口作为"事件回调"流出,一切外部能力都通过 ExecutableTool 作为"统一工具"流入。

四层抽象

① Renderer Layer · 事件汇聚
  • CodingAgentRenderer(接口) → 5 个 Kotlin 实现 + 4 个 TypeScript 实现
  • Default / Compose / Jewel / ServerSide / JsRendererAdapter(Kotlin) · Base / Cli / Tui / Server(TS)
  • 方法级回调:renderIterationHeader · renderLLMResponseChunk · renderToolCall · renderToolResult · renderThinkingChunk · renderFinalResult
② Executor Layer · Agent 主循环
  • CodingAgentExecutor.execute() 多轮 loop + Token 计量 + 终止条件
  • ConversationManager 维持完整 message 历史,支持 continue / new / 自动压缩
  • ToolCallParser 解析 LLM 响应里的工具调用片段
  • 重复检测 + 卡死检测 → 自动派发 ErrorRecoveryAgent
③ Orchestrator Layer · 策略与协调
  • ToolOrchestrator.executeToolCall() 统一入口
  • 执行前调用 PolicyEngine.decide():ALLOW / DENY / ASK_USER
  • LiveShellExecutor 支持 PTY 流式输出
  • McpToolAdapter 把 MCP Server 暴露的工具伪装成本地 tool
④ Tool Layer · 所有能力的统一接口
  • 所有能力(内置工具 / MCP 工具 / SubAgent)都实现 ExecutableTool<TParams, TResult>
  • Schema 采用手写 + 声明式(DeclarativeToolSchema + SchemaPropertyBuilder),不用反射/KSP——KMP 兼容考虑
  • 工具 metadata 带 displayName / emoji / icon / schema,供 Renderer 直接使用

引擎分层架构图

DevIns DSL:被很多人忽略的关键一环

devins/ 是一个完整的 DSL 编译器栈 — Lexer → Parser → AST → 多 Processor → 输出。 它把"自然语言 + 代码 + 工具调用"混写成一种 Markdown-like 格式,举例: 

---
title: Create REST API
---

The API should have three endpoints: /list, /detail, /create.

/shell command="mkdir -p src"
/read-file path="src/api.ts"

Now analyze what needs changing.

它解决纯工具调用的三个短板:(1) 条件/循环难表达;(2) 自然语言和参数易混淆;(3) 批量操作繁琐。并且有专用的 IntelliJ 语言插件和 TS LSP 提供自动补全。

05KMP 跨端一致性的五层手法

要让同一套 Agent 引擎跑到 8 种宿主并保持一致体验,必须有一套分层适配方案。AutoDev 给出的答案是"五层递进式的分离与适配"。

Layer 1 代码层:expect/actual

平台差异封到类型系统内。Platform.kt 在 commonMain 用 expect object Platform 定义接口,在 jvmMain / jsMain / iosMain / wasmJsMain / androidMain 各给 actual 实现。

检测 / Shell / FileSystem / Log / reduce-motion · 全部走 expect/actual

Layer 2 导出层:@JsExport

把 Kotlin 类型规范化到 TS 可消费的形式。三个硬约束:只导出 concrete class(不导 interface);异步用 Promise(不用 Flow);集合用 Array(不用 List)。

JsCodingAgent · JsCodingAgentRenderer · JsStepSummary · JsTaskSummary

Layer 3 渲染层:9 个 Renderer

同一个 CodingAgentRenderer 接口 → 5 Kotlin + 4 TS 实现。AGENTS.md 规定"修改接口必须同步 9 处",这是显式规范而不是工具检测。

Default · Compose · Jewel · ServerSide · JsAdapter · Base · Cli · Tui · Server

Layer 4 设计层:Token 双写同步

Compose 色板(AutoDevColors.kt)和 TS 色板(colors.ts)用同一份文档(design-system-*.md)双写——用户色 #00F3FF · AI 色 #D946EF 完全一致。没用共享常量库,靠纪律而不是工具。

Layer 5 组装层:Composite Build + 全局排除

IDEA 插件走 includeBuild("mpp-idea") 独立 Gradle,可用不同插件版本不污染主项目。主项目用 exclude(group = ...) 把 Tika / AWS / PlantUML 等重依赖剔除,让不同宿主按需瘦身。

Layer +1 构建层:TS 定义自动生成 + WASM 字体下载

Kotlin/JS 开 generateTypeScriptDefinitions() 自动产 .d.ts,TS 侧获得完整类型。WASM Canvas 中文渲染通过 build-time 下载 Noto Sans CJK(不提交字体到 Git)。

@JsExport 使用范式(典型代码)

07关键设计决策拆解

挑 7 个"如果不看代码很难看出"的关键决策,每个都是架构层面的取舍。

D1 · 为什么不是纯 JVM,而是 Kotlin Multiplatform?

同一套 Agent 引擎要同时上 IDEA / VSCode / CLI / Desktop / 移动 / Web / Server。纯 JVM 在浏览器和移动端打不赢;Electron/Tauri 又失去原生体验和轻量性。

赢在:~70% 核心代码共享;原生 bundle 轻量(无 Chromium);同一份 Agent/Tool/MCP 集成到任意端。
付出:expect/actual 心智;Kotlin/JS 导出 TS 有硬约束;iOS 构建最易崩;团队门槛高。

D2 · 为什么 Renderer 有 9 个实现,而不是一个通用 renderer?

每个宿主的 UI 原语不同:IDEA 用 Jewel Compose;VSCode 用 Webview;CLI 用 ANSI;Server 用 SSE。一个抽象统一不了这些底层差异。

赢在:UI 完全脱耦、可选择性实现(CLI 可以跳过 renderThinkingChunk);接口定义"事件"而非"命令",更灵活。
付出:加新回调要改 9 处;全靠 AGENTS.md 文档规范,没有编译时检查;可能做少了某些端的方法。

D3 · 为什么 SubAgent 是"一类 Agent"而不是普通函数?

SubAgent 需要独立的 LLM 上下文、独立的工具白名单、独立的状态持有;普通函数给不了这些。把它设计成 ExecutableTool 的一种变体,意味着主 Agent 调子 Agent 和调工具的接口完全统一。

赢在:组合性强 · 权限隔离 · 状态保持 · 运行时可注册/注销 · 天然支持递归分派。
付出:一次 SubAgent 调用 = 一次新 LLM 会话成本,慎用;SubAgent 之间的互调目前未启用。

D4 · 为什么工具 Schema 全是手写,不用反射/KSP?

KMP 环境下反射在 JS/WASM 开销太大,KSP 无法跨平台运行。宁可牺牲代码重复,也要换来跨平台一致和运行时零反射。

赢在:编译期完成 Schema;JS/WASM 零反射;枚举/必填/验证规则显式可见。
付出:参数定义要写两遍(Kotlin 类 + Schema);修改工具容易忘同步。

D5 · 为什么错误恢复分"工具层"和"Agent 层"两处?

技术错误(权限失败、超时、异常)应该在 ToolOrchestrator 层直接处理;智能错误(命令本身跑错了、测试不过、思路错了)则需要 LLM 再次参与。强行合并会让"是否该上升到 LLM"的判断丢失。

赢在:ErrorRecoveryAgent 只在真正需要的时候被触发(重复 3 次同工具失败);工具层的异常不浪费 LLM token。
付出:两层判断逻辑需要维护;"什么算重复失败"的阈值是魔法数字。

D6 · 为什么 VSCode 扩展是"纯 TS + bridge",不共用 Compose?

VSCode API 强绑定 JS/TS 生态,Webview 只能跑 HTML/JS。用 Compose for Web 虽然可以,但 bundle 体积和调试复杂度不可接受。

赢在:VSCode 发布流程独立、快;TS 开发者直接上手;扩展包体积可控。
付出:Webview 组件要用 TS 再写一遍,UI 和 Compose 端不完全一致。

D7 · 为什么 DevIns DSL 存在,但不强制所有用户用?

大多数场景下纯工具调用够用;只有在"命令 + 参数 + 逻辑 + 自然语言"混杂时,DSL 才有表达力优势。强推反而增加学习成本。

赢在:复杂工作流可以 DSL 一键编排;IDE/LSP 提供补全;Velocity 表达式支持动态插值。
付出:DSL 采用率低,投入产出不明显;只在首轮编译,LLM 响应里的 DSL 块无法再次编译。

08生态战略:不做围墙的平台

AutoDev 在生态层的 5 个选择,本质上都在表达同一件事:"我们不做孤岛,我们做其他 AI 工具的宿主"。

① MCP(Model Context Protocol)

任何符合 MCP 的 Server(Brave Search / Linear / GitHub / Notion…)都能通过 McpToolsInitializer 自动加载成本地 Tool。AutoDev 不需要为每个外部服务写适配,社区工具生态即所得。

② AGENTS.md

项目级规则以 Markdown 形式躺在 repo 根目录,Agent 启动时沿目录树自动发现、层级合并并注入系统 prompt。规则随代码版本管理,不是中央平台配置猜测。

③ Claude Skill

直接支持加载 Anthropic Claude Skill 格式,团队可以把工作流写成 Skill 包共享。AutoDev 把 Skill 当成"可移植的工作流单元",借 Anthropic 的生态势能。

④ SpecKit 命令集成

把 SpecKit(规格驱动的命令系统)接入 Agent,让"先写 spec 再执行"这种工程实践成为一等公民。

⑤ A2A(Agent-to-Agent)协议

允许用户编排"Agent A 产出 → Agent B 审 → Agent C 修"这种跨 Agent 的自动化流水线,AutoDev 做编排宿主。

⑥ 多 LLM Provider

OpenAI / Anthropic / Google / DeepSeek / Ollama / GLM / Qwen / Kimi 统一抽象。国产模型完整支持 + 中英双语 i18n = 中国市场第一梯队布局。

产品洞察:当市场认为 AI 编码工具的胜负在"模型 + IDE 打磨"时,AutoDev 押注的是"工具联邦的宿主"这个更上位的品类。 这个选择的赔率很高:赢的话它是 AI 开发工具的 VS Code(宿主);输的话它会被单点工具用户体验压死。

09四视角洞察汇总

产品 用户 架构 工程

【产品视角】

  • 品类定位新而陡:定义"工作流编排 + 全端投送"这个新品类 — 独到,但需要教育市场。
  • 6 大阶段自然衔接是最大卖点:同一个会话里跨 Document → Coding → Review → ChatDB → Artifact,其他工具靠人肉复制粘贴。
  • 开放生态赌未来:MCP + AGENTS.md + Claude Skill + SpecKit + A2A——每一个都不是 AutoDev 独创,但"全都支持"本身就是护城河。
  • 国际化是战略:中英 i18n + 国产 LLM 全接入 = 明确针对中国开发者 + 保留全球可能性。
  • 当前处于 Alpha:README 自标 Alpha,模块层面也能看到部分能力(Web / Test Agent)仍是 experimental,定位还在收敛。

【用户视角】

  • "我在哪里工作,它就在哪里":IDE 党用 IDEA 插件,前端党用 VSCode 扩展,CLI 党用 npm 包,产品党用 Desktop App。
  • 阶段切换零成本:写完代码直接让同一个会话 review,review 出问题直接修——不切工具、不丢上下文。
  • 团队规则自动继承:AGENTS.md 让新人拉到 repo 就有"老手的心智模型",不需要口头传承。
  • 潜在体验风险:多端体验并非完全对齐(Webview 版 vs Compose 版 UI 细节有差),学习曲线比 Cursor 陡。
  • 对"写代码"用户直接收益;对"做原型"用户(ArtifactAgent)是惊喜;对"查数据"用户(ChatDBAgent)是刚需。

【架构师视角】

  • 四层抽象清晰:Renderer / Executor / Orchestrator / Tool 四层完全解耦,每层都能单测。
  • "工具即接口"的彻底贯彻:SubAgent 也是工具,MCP 工具也是工具,DevIns 编译后还是工具调用——一个接口治所有外部能力。
  • 事件驱动的 Renderer 模式比"命令驱动"更符合 AI loop 的本质:LLM 的输出本就是流式事件,UI 订阅感兴趣的事件即可。
  • 错误恢复两层分离(Tool 层技术错误 / Agent 层智能错误)是值得对标的做法,避免什么错都扔给 LLM。
  • Plan / Tracker 可观测:任务状态变化有事件回调,UI 能实时显示进度——这在长 Agent 任务里是用户耐心的关键。

【工程师视角】

  • Composite Build 的聪明用法:IDEA 插件独立 Gradle 版本,不污染主项目,又能共享 mpp-core(用 mavenLocal 中转)。
  • 全局 exclude 瘦身:Tika / AWS SDK / PlantUML 等重依赖在根 build 里 exclude,每个宿主按需保留——否则 bundle 会炸。
  • @JsExport 的硬约束(只导 class / Promise / Array)需要团队纪律,没有 lint 能保证。
  • i18n 双轨手写(i18n4k + TS locale):宁可多人工也要保证一致,反映了团队对跨端复杂度的务实取舍。
  • 设计 Token 双写:Compose 色板和 TS 色板完全对齐,但用的是"抄文档"而不是"共享库",避免 KMP 资源管道复杂度。
  • WASM 中文字体 build-time 下载是个精妙的工程解法:代码库不肿胀,运行时体验不掉。

10可高度提炼的核心思想

脱离具体代码,这些是可以抽象到任何语言、任何形态的 AI Agent 系统的架构方向。

① 工具是 Agent 的唯一一等公民

不要设计"超级 Agent",要设计"可组合的 Tool"。SubAgent 是 Tool,MCP 调用是 Tool,DSL 编译产物也是 Tool——一个接口把所有外部能力、所有 Agent、所有执行都统一。这样热插拔、权限、监控才可能统一实现。

② Renderer 是事件的汇聚,不是命令的分发

执行引擎不直接调用 UI,而是在关键节点触发 renderer 的回调。UI 可以只订阅感兴趣的事件(IDE 不关心 thinking chunk,CLI 不关心 chart block)。这比"发指令给 UI"灵活一个维度。

③ 对话必须有状态,错误必须分层

ConversationManager 维持完整历史支持中断/恢复,才有可能做长任务。错误分"技术错误(Tool 层)"和"智能错误(Agent 层)",前者不浪费 LLM token,后者才让 SubAgent 介入。

④ 权限在编排层集中,不在工具里散落

PolicyEngine.decide() 在 Orchestrator 一处决定 ALLOW/DENY/ASK_USER,而不是每个工具自己判断。这样"审批流"才有可能加得上。

⑤ 项目规则是代码,不是配置

AGENTS.md 放在 repo,随代码版本管理,Agent 自动发现、层级合并。不是让平台猜,不是让用户设,而是让项目自己说——这对团队协作意义重大。

⑥ 生态适配比功能自建更重要

MCP / Claude Skill / SpecKit / A2A——不要自造协议,要成为已有协议的最佳客户端。这是 AI 工具联邦时代的生存策略。

⑦ DSL 是选项不是必须

DevIns DSL 证明:当"命令 + 参数 + 逻辑 + 自然语言"混杂时 DSL 有价值,但不强推;给进阶用户一个可选的表达力升级,而不是给所有用户强制学习成本。

⑧ 跨端一致靠纪律 + 契约,不靠魔法

AutoDev 用 9 个 Renderer 显式实现、设计 Token 双写、i18n 双轨手写——没有一个用魔法自动同步。这告诉我们:跨端一致性在工程上是人力问题,不是技术问题。

11风险与挑战

R1 · 摊子铺得太大

6 主 Agent × 9 SubAgent × 8 宿主 × 多 LLM = 组合爆炸。每一个组合都要测试、维护、支持,单点能力无法与垂直工具(Cursor / Sqrutiny / v0)正面竞争。

R2 · 用户认知混乱

IDE 插件?独立 App?CLI?Web SaaS?一个用户第一次听说 AutoDev,很难一句话说清"它是什么、给我用哪个"。市场教育成本高。

R3 · KMP 稳定性税

iOS 构建、WASM 字体、Kotlin/JS TS 定义生成限制、expect/actual 调试难度——每一项都是真实工程成本。团队一旦走人,后人接手极痛。

R4 · 9 个 Renderer 的一致性靠纪律

AGENTS.md 规定修改接口要同步 9 处,但没有编译时检查。接口增长一次,就有漏改的风险。

R5 · DSL 采用率风险

DevIns DSL 投入了完整的编译器栈 + IDEA 语言插件,但实际用户是否会用仍不明朗。如果采用率低,这部分投入回报率会被质疑。

R6 · 与 Claude Code 范式的张力

Claude Code 代表"纯 Agent + Tool"的简洁路线,并且在用户体验上迭代很快。AutoDev 的"大而全"如果不能在某个阶段明显胜过 Claude Code 的对应场景,会被蚕食。

13对 zCli 的启示

zCli 是 TypeScript + React/Ink 的类 Claude Code CLI,形态比 AutoDev 聚焦很多。但 AutoDev 的几个架构抉择对 zCli 有直接启发价值。

✅ 直接可以借鉴的

  • Renderer 事件汇聚模式:zCli 的 useChat hook 已经类似,但可以进一步抽象 "Renderer" 接口,让未来 Web/IDE 宿主复用同一套引擎。
  • SubAgent = Tool 的统一模型:zCli F13 已实现 SubAgent;可以评估是否进一步"把 SubAgent 纯粹当作 Tool 注册到 ToolRegistry",简化调度链。
  • 错误恢复两层分离:tool 层只处理技术错误,智能恢复交给一个独立的"Recovery SubAgent";zCli 当前是否明确分层值得检视。
  • 权限集中在 Orchestrator:把 policy 决策集中,不要散落在每个工具里。
  • AGENTS.md 层级注入:zCli 应检查自己的 CLAUDE.md 发现策略是否支持多层合并。

⚠ 需要审慎评估的

  • DevIns DSL:为 zCli 量级可能偏重;如果要做,先做"最小表达力"的轻量版。
  • 9 个 Renderer:zCli 现在只做 CLI/TUI,不需要这么多实现,但"接口为事件,不为命令"的原则要提前定下。
  • 全端 KMP:zCli 是 TS 为主,不需要 KMP;但可以学"核心逻辑/UI 分离"的思路,让 core 可被其他前端复用。
  • 大而全的 Agent 家族:不要学,zCli 应该聚焦 Coding Agent + 精选 SubAgent,先打透一个场景。
一句话结论:AutoDev 的"抱负"zCli 不必学,但它的"四层抽象 · 工具即接口 · 事件驱动的 Renderer · 错误分层"这 4 条工程原则,是任何一个认真做 Agent 引擎的项目都值得参考的。
